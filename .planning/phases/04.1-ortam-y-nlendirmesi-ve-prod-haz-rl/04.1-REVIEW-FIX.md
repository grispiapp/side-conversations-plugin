## Fixed Issues

### CR-01: `isGrispiEnvironment` allowlist is bypassable via the prototype chain

**Files modified:**

- `src/grispi/client/environment.ts`
- `src/lib/__tests__/grispi-environment.test.ts`
- `src/lib/__tests__/standalone-dev.test.ts`

**Commit:** `2216fe2`

**Reproduced before fixing.** Confirmed in node that `"__proto__"`, `"constructor"`,
`"toString"`, `"valueOf"` and `"hasOwnProperty"` all return `true` for
`key in GRISPI_BASE_URLS` while `Object.prototype.hasOwnProperty.call` returns
`false`, and that the subsequent lookup yields an `object` / `function` rather
than a host string.

**Applied fix:**

1. **Guard (`src/grispi/client/environment.ts:29-36`)** — replaced
   `value in GRISPI_BASE_URLS` with
   `Object.prototype.hasOwnProperty.call(GRISPI_BASE_URLS, value)`. The
   `typeof value === "string"` guard and the type-predicate signature
   `(value: unknown) => value is GrispiEnvironment` are unchanged, so both call
   sites (`resolveGrispiEnvironment` in `src/lib/grispi-environment.ts:59` and
   `resolveStandaloneDevConfig` in `src/lib/standalone-dev.ts:80`) keep
   narrowing correctly — verified by a clean `tsc --noEmit`. Added a docblock
   explaining why `in` must not be used here, so the change is not silently
   reverted later.

2. **Regression coverage at the guard level** (`grispi-environment.test.ts`) —
   an `it.each` asserting `isGrispiEnvironment(key) === false` for all five
   inherited prototype keys, plus a loop asserting no inherited key ever clears
   the allowlist.

3. **Regression coverage end-to-end through the tenant setting**
   (`grispi-environment.test.ts`) — an `it.each` asserting
   `resolveGrispiEnvironment({ _grispi_env: key }, token)` returns `"prod"` and
   emits the `console.warn` (previously the warn branch was never reached
   because the key was accepted as valid). One further test asserts a
   prototype key still falls through to the JWT `dev: true` → `preprod` branch
   rather than being treated as an explicit environment.

4. **Regression coverage through the standalone dev path**
   (`standalone-dev.test.ts`) — an `it.each` asserting
   `REACT_APP_DEV_GRISPI_ENV=<prototype key>` falls back to
   `DEFAULT_DEV_ENVIRONMENT` (`preprod`), and that the resulting key indexes
   `GRISPI_BASE_URLS` to an actual `https://` **string** (this last assertion is
   what would have caught the original bug — the pre-existing negative test only
   probed `"https://evil.example.com"`, which fails the check for an unrelated
   reason).

**Verification performed:**

- **Negative control:** with the fix reverted but the new tests in place,
  `2 failed / 17 tests failed`. With the fix applied, `2 passed / 42 passed`.
  The new tests genuinely fail against the vulnerable guard rather than passing
  vacuously.
- `npx tsc --noEmit` — clean.
- Full suite via `CI=true npx craco test --watchAll=false` — **30/30 suites,
  384/384 tests passed** (up from 367; +17 new).
- Static prohibition gate
  `grep -rn "grispi\.\(net\|com\)" src --include="*.ts" --include="*.tsx" | grep -v __tests__ | grep -v environment`
  — empty output, still passing.
- `npx prettier --check` on the three modified files: `environment.ts` is clean;
  the two test files still carry only their **pre-existing** IN-01 violations
  (verified by diffing prettier's canonical output — every remaining hunk
  predates this commit). My additions were hand-formatted to prettier style so
  this fix adds no new formatting debt and does not silently absorb IN-01.

**Note on the optional hardening:** the review also suggested defence-in-depth
(null-prototype map via `Object.create(null)`, or asserting the looked-up value
starts with `https://`). That was **not** applied — it is explicitly optional in
the review, changes the shape of `GRISPI_BASE_URLS` (and therefore
`keyof typeof`), and is outside the narrowed scope of this pass. Worth
considering in a follow-up.
