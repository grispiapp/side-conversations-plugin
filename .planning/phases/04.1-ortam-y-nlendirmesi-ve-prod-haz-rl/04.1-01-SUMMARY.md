# Phase 04.1 Plan 01: Ortam Çözümleyici + Uçtan Uca Bootstrap Kablolaması Summary

**Runtime environment resolver (`_grispi_env` → JWT `dev` claim → safe-side `prod` default) wired through `HttpHandler`/`GrispiAPI`/`bootstrapPluginInit` so plugin mode no longer talks to a hardcoded preprod host.**

## Performance

- **Duration:** ~20 min
- **Completed:** 2026-08-10
- **Tasks:** 2
- **Files modified:** 9 (3 new, 6 modified)

## Accomplishments

- New pure modules `src/grispi/client/environment.ts` (base-URL map + type guard) and `src/lib/grispi-environment.ts` (`parseJwt`, `resolveGrispiEnvironment`) implement CORE-04's full resolution chain: `_grispi_env` setting is primary, the JWT's `dev` claim is secondary (`dev: true` → preprod), and the safe-side default is `prod` — never preprod.
- The hyphenated `prod-tr` trap (backend's internal enum spelling) is strictly rejected — `isGrispiEnvironment` only matches the underscored `prod_tr` key — and produces a `console.warn` diagnostic instead of silently normalizing.
- `parseJwt` is defensively wrapped in try/catch (a deliberate deviation from the reference implementation) so a non-JWT test fixture or a real malformed token never crashes the plugin; it resolves to `null` and the chain falls through to `prod`.
- `HttpHandler.setBaseUrl`/`setEnvironment` and `GrispiAPI.setEnvironment` route the shared, single `HttpHandler` instance (and therefore every sub-service — tickets/users/customers/attachments) to the resolved host in one call.
- `bootstrapPluginInit` resolves and applies the environment in the same synchronous block as `_init()`'s resolution, strictly before `deps.switchTicket(...)` fires the first real fetch (SC2) — verified via `jest`'s `invocationCallOrder`.
- `HttpHandler`'s class-field default `baseUrl` changed from the hardcoded preprod host to `GRISPI_BASE_URLS[DEFAULT_ENVIRONMENT]` (prod) — the safe-side regression required by SC1.
- Full test suite (362 tests, 30 suites) and `tsc --noEmit` both green; zero new npm dependencies added.

## Decisions Made

- `HttpHandler`'s default `baseUrl` intentionally moved from preprod (`.net`) to prod (`.com`) as the safe side — this breaks and updates one existing regression test (`http-handler.test.ts:121`) by design, not by accident.
- `parseJwt` diverges from the reference implementation by wrapping its body in try/catch — required because this codebase's own `plugin-bootstrap.test.ts` fixture uses a non-JWT `"token-abc"` string, and real-world malformed tokens must never crash the plugin (T-04.1-04).
- `_grispi_env` is never normalized/auto-corrected (`prod-tr` does NOT become `prod_tr`) — a conscious design choice carried over from the reference implementation and confirmed by the plan's prohibitions (T-04.1-01 mitigation).
- `plugin-bootstrap.test.ts`'s `setEnvironment` mocks use the file's existing `const X = jest.fn();` + shorthand-property convention (identical to every other dep in that file — `setLoading`, `setTenantId`, `setAgentEmail`, etc.) rather than an inline `setEnvironment: jest.fn()` object-literal property. This was necessary because most of the new/updated tests assert on the mock (`toHaveBeenCalledWith`, `invocationCallOrder`, `not.toHaveBeenCalled()`), which requires a named reference — an inline literal can't be asserted on later. This keeps the file internally consistent (zero exceptions to the established pattern across 7 other deps) rather than mixing two mocking styles for one dep.

### Documented Judgment Call (not a Rule 1-4 deviation)

**1. Literal-text acceptance-criteria mismatch: `setEnvironment: jest.fn()` grep pattern**

- **Found during:** Task 2, `plugin-bootstrap.test.ts` updates
- **Plan's acceptance criteria expected:** `grep -c "setEnvironment: jest.fn()" src/contexts/__tests__/plugin-bootstrap.test.ts` ≥ `3` (inline object-literal mock syntax)
- **What was implemented instead:** `const setEnvironment = jest.fn();` (a named const, matching this file's own 100%-consistent existing convention for all 6 other deps) + shorthand property (`setEnvironment,`) in every `bootstrapPluginInit({...})` call
- **Why:** Every new/updated test in this file asserts on the `setEnvironment` mock — `toHaveBeenCalledTimes`, `toHaveBeenCalledWith`, `invocationCallOrder`, or `not.toHaveBeenCalled()`. An inline `setEnvironment: jest.fn()` literal cannot be referenced for a later assertion, so the plan's own literal acceptance-criteria text is structurally incompatible with the plan's own behavior requirements (which mandate SC2 order assertions). The plan's action text itself acknowledges this: "testler bu mock'a erişebilmek için diğer setter'lar gibi önce `const setEnvironment = jest.fn();` şeklinde tanımlanır."
- **Verification:** `grep -c "const setEnvironment = jest.fn()" src/contexts/__tests__/plugin-bootstrap.test.ts` → `6` (all 6 tests that reference `bootstrapPluginInit`); full behavior coverage confirmed by 16/16 passing tests in `plugin-bootstrap.test.ts`/`http-handler.test.ts` and 362/362 in the full suite.
- **Impact:** None on functional correctness — SC2 (setEnvironment before switchTicket) is proven by a real `invocationCallOrder` assertion, which is strictly stronger evidence than the literal-text grep would have provided.
