# Phase 4 — UI Design Contract

> Visual and interaction contract for Phase 4: Dosya Ekleri ve Inline Görseller. Generated by gsd-ui-researcher, verified by gsd-ui-checker. Converts `04-CONTEXT.md`'s 22 locked decisions into pixel/copy/state contracts; does not revisit them.

**Scope:** the attach toolbar button, the attachment chip list (composer panel slot above the toolbar), per-chip upload/failed/idle states, the send-lock explanation, drag-and-drop, inline pasted-image states in the editor, toast-based error surfacing (new `sonner` dependency), and incoming/own attachment rendering in `ThreadMessage`. Out of scope: talep özeti alıntılama, alıcı geçmişi, sessiz tazeleme (Faz 5).

**Design system continuity:** palette, base spacing tokens, and the 3-role typography scale are carried over verbatim from `03-UI-SPEC.md` (approved). This phase adds exactly one new dependency to the visual system: shadcn official `sonner` (toast). No new colors, no new base type sizes.

## Attachment & Inline Image Contract

### 1. Attach button (D-04)

- New `ToolbarCommand` value `"attach"`, icon `FilePlusIcon`, `aria-label`/`title` **"Dosya ekle"**.
- **Position: first item in `TOOLBAR_ACTIONS`**, before "Kalın", with its own `groupEnd` divider. Rationale (assumption, flagged): the toolbar already scrolls horizontally at 372px with 9 buttons (D-08); attaching a file is a primary, frequently-used action for this phase (unlike undo/redo), so it must be reachable without scrolling in the narrowest state. Placing it first guarantees this regardless of scroll position.
- Click opens the native file picker via `react-dropzone`'s `open()` (`useDropzone({ noClick: true, noKeyboard: true })` wrapping the composer root — click handling stays owned by this explicit button, not by clicking the editor body).
- `multiple` selection allowed. No `accept` MIME allowlist (D-09) — validation is post-selection (§3).
- Button stays enabled even once 10 files are already attached (D-08's count cap is enforced via rejection toast on the *next* attempt, not by disabling the control — avoids a second implicit state to communicate).

### 2. Drag-and-drop (D-13)

> **Revised 2026-08-01** — D-13 moved from "every drop is an attachment" to **positional routing**. The drag affordance must therefore make the boundary *visible*, since an invisible split at 372px was the original objection to this behavior.

- `useDropzone({ noClick: true, noKeyboard: true })` still wraps the composer root and drives a boolean `dragActive` state via `onDragEnter`/`onDragLeave`/`onDrop`.
- **Two zones, shown only while `dragActive` AND the drag payload is all-images** (`dataTransfer.items` all match `INLINE_IMAGE_MIME_TYPES`):
  - **Editor text area** → *inline zone*: `rounded-md border-2 border-dashed border-primary bg-primary/5`, centered label **"Mesaja göm"** (Başlık role: 14px/600, `text-primary`).
  - **Rest of the composer** (toolbar + chip panel band) → *attachment zone*: same border treatment at `border-primary/40` with the label **"Dosya olarak ekle"** (Meta role: 12px/500, `text-muted-foreground`).
  The two overlays are siblings, `pointer-events-none`, and never overlap — the boundary is exactly the editor's own bounding box, so what the user sees is what `posAtCoords` will resolve.
- **Single zone (whole composer, unchanged from the original spec)** whenever the payload contains **any** non-image file, or the payload type cannot be determined: overlay `inset-0`, label **"Dosyaları buraya bırakın"**, because a mixed drop routes entirely to attachments (D-13 mixed rule). This keeps the promise on screen honest — one gesture, one outcome.
- A visually-hidden `aria-live="assertive"` span announces the destination on `dragEnter`: **"Görseli mesaja gömmek için editöre bırakın, dosya olarak eklemek için dışına bırakın."** for the two-zone case, and the original **"Dosyaları bırakın, ek olarak eklenecek."** for the single-zone case.
- Overlays render above editor content but below the toolbar/chip chrome; z-index stays scoped to the composer section and must not escape into the surrounding thread/list.

### 3. Client-side validation & rejection (D-08, D-09, D-11)

Applied identically to file-picker selection and drop, evaluated per batch (all files dropped/selected together):

1. **Per-file size** > 10 MB → rejected.
2. **Running total** (already-attached + this batch's accepted files) > 25 MB → reject files from this batch, in order, until total is back under 25 MB (earlier files in the batch win).
3. **Count**: total attached (existing + newly accepted) > 10 → reject the overflow, in order.
4. No MIME/extension filter (D-09) — everything else is accepted.

Accepted files are added immediately as chips and begin uploading (§5). Rejected files never appear as chips. All rejections from one batch are summarized into **one** toast (§7) — never one toast per file, to avoid pile-up when many files are dropped at once.

### 4. Attachment chip list — placement, threshold, disclosure (D-01, D-02, discretion resolution)

**Placement (D-01):** renders inside `rich-text-composer.tsx`'s existing bottom `<div className="border-t border-border bg-card">` panel slot (the same container that hosts `headingMenuOpen`/`linkEditorOpen`). Order top-to-bottom inside that container: **attachment area** (if any files) → heading menu (if open) → link editor (if open) → toolbar row (always). The attachment area is not a toggleable popover like the other two — it is present whenever `attachments.length > 0`, stacking above them.

**Chip is a pill, not a row** (per `badge.tsx`'s existing "chip için temel" note and the decision text's own wording, "3 dosya ▾" — chip/pill vocabulary throughout): `AttachmentChip` visually extends `badgeVariants` with a new **`file`** variant (`rounded-full border border-border bg-muted text-foreground`) — a neutral, non-semantic pill shape distinct from the existing `new-reply`/`awaiting-reply`/`closed` status pills. Whether the executor literally renders `<Badge variant="file">` as the shell or composes matching Tailwind classes in a purpose-built component (chips need icon/text/button child slots Badge's plain `<span>` doesn't naturally host) is an implementation choice — the **visual output must match** `badgeVariants({variant:"file"})`.

Container: `flex flex-wrap items-center gap-1.5`, `role="group"`, `aria-label="Ekler ({n})"`, padding `px-2 py-2` (matches the existing toolbar row's own `px-2 py-2`, keeping the vertical budget tight per D-02), `border-b border-border` separating it from whatever renders below.

**Threshold (resolves the Claude's-discretion note explicitly):**
- **0 files:** area renders nothing (zero height).
- **1–2 files:** every chip renders directly as a pill in the wrap container — no summary.
- **3+ files:** a single summary pill renders: **"{n} dosya"** + `ChevronDownIcon` (not the literal "▾" glyph — see Copywriting note below), acting as a disclosure toggle (`aria-expanded`, `aria-controls` pointing to the chip list's id).
  - **Collapsed:** only the summary pill shows; individual chips are hidden.
  - **Expanded:** the summary pill stays visible (chevron rotates 180°, `transition-transform`), followed in the same `flex flex-wrap` row by every individual chip.
- **Default-state rule (resolves the "see what you uploaded" tension):** auto-collapse only applies at the moment a composer session is entered with **3+ files already present** (e.g., resuming a draft). A **live transition from below-threshold to 3+** (user adds a 3rd file while watching the first two upload) does **not** auto-collapse the list — it stays expanded until the user manually collapses it. This prevents a file the user just watched upload from visually "disappearing" the instant it crosses the threshold.
- Removing a chip back down below 3 always shows the remaining chips directly (summary pill disappears entirely, no leftover toggle state).

### 5. Per-chip upload states (D-05, D-06, D-07)

Files upload to `POST {BASE}/attachments/upload` **immediately on selection/drop** (D-05), independent of send. Each chip pill has 3 states:

**Idle / uploaded** (default once the 200 response with `id`/`objectUrl`/`size` lands):
- Leading 24px circular slot (`size-6 rounded-full overflow-hidden shrink-0 bg-card flex items-center justify-center`):
  - `image/*` except SVG → real thumbnail, `<img src={localObjectURL} className="size-full object-cover">` (kept as the **local** `URL.createObjectURL(file)` for the chip's lifetime — never swapped for the remote `objectThumbUrl`, avoiding a redundant fetch; revoked with `URL.revokeObjectURL` on unmount/removal).
  - `image/svg+xml` → `ImageIcon` (14px, `text-muted-foreground`) — **no thumbnail**, consistent with D-10's "never embed SVG in our own panel" rule applied uniformly to every surface (composer chip *and* thread render, §9), even though D-10's literal text sits under the incoming-attachments decision. The icon still signals "this is an image" without rendering pixel data.
  - `application/pdf` → `FileTextIcon`.
  - `video/*` → `VideoIcon`.
  - everything else → `FileIcon` (generic).
- Text: single line, Meta/etiket role (12px/500) — **"{filename} · {size}"**, filename part `text-foreground font-medium`-weight-500 (reusing the existing 500 weight already declared for Meta/etiket, not a new weight), size part `text-muted-foreground`. Filename is middle-truncated (see algorithm, Copywriting section) to a max ~14–16 visible characters given the pill's `max-w-[180px]` cap.
- Trailing: 20px circular ghost remove button, `Cross2Icon` (10px), `aria-label="{filename} dosyasını kaldır"`.

**Uploading:**
- Leading slot shows `ReloadIcon` (12px, `animate-spin`, `text-muted-foreground`) in place of the thumbnail/icon.
- Text becomes **"{filename} · Yükleniyor…"** (size text replaced — filename itself is already known locally from the `File` object, so it still displays).
- **Progress format resolution (Claude's discretion):** **indeterminate spinner**, not a percentage. No byte-level upload-progress wiring is confirmed available (single multipart POST, no chunked/XHR-progress contract established in research), and the existing project has no percentage progress-bar component (`animate-loading-progress` keyframe is used exactly once, indeterminately, in `loading-screen.tsx`). A spinner is simpler, matches that one existing precedent, and keeps the chip single-line.
- Remove button stays enabled. Removing a still-uploading chip does **not** cancel the network request (no `AbortController` this phase, per CONTEXT's deferred item) — the request completes and becomes an orphaned server file, the same accepted trade-off already stated in D-05/D-17.

**Failed** (network error or non-2xx from the upload POST):
- Leading slot background becomes `bg-destructive/10`; icon `ExclamationTriangleIcon` (12px, `text-destructive`).
- Text: filename, then a **destructive-colored inline button** (not plain text) reusing `ThreadMessage`'s exact retry-copy duality (D-07 cites this precedent directly):
  - Network failure → **"{filename} · Bağlantı sorunu · Tekrar dene"**
  - Server/HTTP failure (generic) → **"{filename} · Yüklenemedi · Tekrar dene"**
- Clicking "Tekrar dene" re-POSTs the same `File` object. Remove button still present (user can discard instead of retrying).
- Chip pill border/background otherwise unchanged (`border-border bg-muted` — only the leading icon slot and trailing text tint destructive, matching the project's existing "color never carries meaning alone" rule — text explicitly says what's wrong).

### 6. Send-button lock (D-06)

- `Gönder` is disabled whenever **any** chip is in the `uploading` state, in addition to its existing disabled conditions (empty content, `submitDisabled`, `submitting`, `!editor`).
- **Explanation placement (discretion resolution):** no new persistent row is added to the already-tight bottom toolbar strip. Instead:
  - The primary **visible** signal is each chip's own "· Yükleniyor…" text (§5) — already directly above the locked button, in the same panel.
  - The button additionally carries `aria-describedby` pointing to a visually-hidden (`sr-only`) span rendered only while at least one chip uploads: **"Ekler yükleniyor, gönderim şu anda kilitli."** — this satisfies D-06's "kısa açıklama gösterilir" for assistive tech without adding new visible chrome that would eat into D-02's protected vertical budget.
  - `title="Ekler yükleniyor…"` on the disabled button as a native-tooltip fallback for sighted mouse users who hover a disabled control.

### 7. Toast mechanism — sonner (D-12) and error routing

`sonner` is added via `npx shadcn add sonner` (shadcn official — no third-party registry vetting required). One `<Toaster />` mounted once at the app root (not per-screen).

**Placement/sizing (must not obscure the composer, per CONTEXT's explicit concern):**
- `position="top-center"`, offset below the fixed header: `top: calc(var(--panel-header-height) + var(--panel-inset))` (≈ 64px), so it never overlaps `ScreenHeader` and never competes with the bottom-pinned composer.
- Width constrained to the panel: `w-[calc(100%-2rem)] max-w-[340px]` (respects `--panel-inset: 1rem` on both sides).
- `duration`: 5000ms for the (potentially multi-line) rejection summary, 4000ms for single-line errors. Always includes a visible close (`Cross2Icon`) affordance — never relies purely on auto-dismiss.
- Visual: destructive/error toasts reuse the existing inline-alert color language rather than inventing new toast chrome — `border-destructive/30 bg-card text-foreground`, `ExclamationTriangleIcon` (destructive) leading icon. No new color role introduced.

**Error routing table (resolves "which errors go to toast vs inline"):**

| Error | Surface | Rationale |
|---|---|---|
| Partial rejection (size/count/total-size, D-11) | **Toast** | About files that were never added; doesn't block the composer; transient |
| Attachment upload failure (post-selection network/server) | **Inline** — chip stays in `failed` state (§5) | Actionable, tied to a specific object that persists in the composer for retry (D-07) |
| Inline pasted-image upload failure (§8) | **Toast** | Transient, no retry affordance exists for this path (D-14) |
| Send blocked while uploading (D-06) | Neither — chip status + `aria-describedby`, not an error | Not a failure state |

### 8. Inline pasted image (D-14, COMP-08)

Paste-only (Tiptap `@tiptap/extension-file-handler`'s `onPaste`, per D-13/CONTEXT's code trap #1 — `handlePaste` must return `false` when `event.clipboardData?.files.length` so FileHandler can take over).

1. On paste, upload starts immediately (`?inline=true`). A **placeholder** `<img>` is inserted at the cursor using a **local `URL.createObjectURL(file)`** (not base64, per research's memory guidance), wrapped so it can carry a `data-uploading="true"` marker for later swap.
2. **Uploading placeholder visual:** the placeholder image renders at `opacity-70`; a small circular status badge overlays its bottom-right corner (`absolute bottom-1 right-1 size-5 rounded-full bg-card/90 shadow flex items-center justify-center`, `ReloadIcon` 12px `animate-spin`).
3. **Resolved:** `src` swaps to the returned `objectUrl` (local blob URL revoked), uploading badge/opacity removed. Standard `<img>` styling inside `.rich-text-content` (new rule, added to `src/index.css`):
   ```css
   .rich-text-content img {
     @apply my-2 block max-h-[240px] w-auto max-w-full rounded-md border border-border object-contain;
   }
   ```
   Left-aligned (no `mx-auto` — matches the project's existing left-flow paragraph/list alignment; nothing in `.rich-text-content` is ever centered). `max-h-[240px]` prevents one large screenshot from dominating the 372px composer (which already scrolls internally at 5–6 lines per D-07); width always constrained to the column via `max-w-full`.
4. **Failure:** placeholder is removed entirely from the editor content (no retry — this matches the canonical reference's documented behavior, distinct from D-07's attachment retry). Notification: toast, **"Görsel yüklenemedi, editöre eklenemedi."** (§7 routing table).
5. Inline images never appear in the attachment chip list (D-15) and are garbage-collected at submit per D-16 (id included in `attachmentIds` only if the `objectUrl` still appears in the final body HTML) — this is a data-layer rule with no additional visual contract.
6. Deleting an already-resolved inline image is standard editor text-selection/backspace — no bespoke remove UI is added (unlike attachment chips, which need an explicit remove button because they live outside the text flow).

**Sanitizer policy split (visual consequence, not a new UI element):** the project's single `sanitizeHtml` currently forbids `img` entirely (`FORBID_TAGS`/`FORBID_CONTENTS`, per `html-sanitizer.ts`). This phase requires an **authored-content policy** that allows `img`+`src` (own composed/sent body) while the **remote/incoming policy stays exactly as-is** (D-21 unchanged — incoming message bodies never render `img`). Net visible effect: **own sent messages show their own inline images when redisplayed in the thread; incoming messages never show body images, ever.** `svg` stays forbidden in both policies (D-10). Exact function/policy naming is a planning-level concern (already flagged in CONTEXT's code_context); this spec only fixes the required visible behavior.

### 9. Incoming & own attachments in the thread (D-19, D-20, D-21, D-22, THRD-06)

Renders inside `ThreadMessage`, below the message body / quote-disclosure block, above the pending/failed status row — for **both** `direction === "own"` and `direction === "incoming"` messages whenever `message.attachments` is non-empty (attachments belong to the comment regardless of direction; a temsilci should also see what they successfully attached to their own sent message once it round-trips through the thread).

`inline: true` attachments are **not** filtered out of this list (D-22, deliberate divergence from grispi-ui) — because this plugin never renders incoming body images (D-21), filtering them would make a third party's inline screenshot vanish entirely.

**Layout at 372px — two zones, only the zones with content render:**

1. **Image thumbnail row** (any `image/*` attachment **except SVG**): each renders as a small square thumbnail, `size-[72px] rounded-md border border-border object-cover`, inside `flex flex-wrap gap-2`. This single rule handles 1 image (one 72px square) and many (wraps naturally into additional rows) — no separate "grid vs single" logic needed. Each thumbnail is wrapped in `<a href={objectUrl} target="_blank" rel="noopener noreferrer">` (native semantics + middle-click/ctrl-click support, not a JS `onClick`+`window.open`), `<img alt="{filename}">`, `title="{filename}"` on the anchor for hover identification (no visible caption text under grid thumbnails — keeps the row compact).
2. **File chip row** (PDF, video, generic, and SVG — SVG explicitly excluded from the thumbnail treatment per D-10 uniformly applied, using `ImageIcon` per §5's mapping): each renders as the same `AttachmentChip` pill shell as the composer (§4), but **read-only** — no remove button, whole pill wrapped in `<a href={objectUrl} target="_blank" rel="noopener noreferrer">`, trailing `ExternalLinkIcon` (10px, `text-muted-foreground`) replacing the remove button's position. `aria-label="{filename}, {size}, yeni sekmede açılır"`.

Order when a message has both: image thumbnail row first, then file chip row below it (`mt-1.5` gap) — images read as the "highlight" content, documents/other files as secondary. `objectUrl` is used directly (confirmed auth-header-free per research); no lightbox, no panel-internal preview (D-20 — 372px has no room for one).

## Spacing Scale

Identical base tokens to `03-UI-SPEC.md` — no new tokens introduced:

| Token | Value | Usage |
|---|---:|---|
| xs | 4px | icon/etiket içi boşluk |
| sm | 8px | attachment area padding (`px-2 py-2`), toolbar/chip row rhythm |
| md | 16px | composer section padding, mesaj bloğu iç boşluğu (unchanged) |
| lg | 24px | drag-overlay centered content padding |

Exceptions:
- **Chip/pill height 32px (`h-8`)** — not the generic `--interactive-target` (40px). Matches the existing `size="toolbar"` exception already established in `button.tsx` for this same composer surface (mouse-first, desktop-iframe context, per Phase 2's identical dropdown-row precedent).
- **Micro icon-text gaps below 4px (`gap-1`/`gap-1.5`, 4–6px)** inside chip pills — sub-8pt inline icon-to-label spacing, already the established pattern in the same file's toolbar (`gap-0.5`) and `ThreadMessage`'s status rows (`gap-1`). Used only for icon-adjacent-to-text bonding, never for layout-level gaps.
- **Image thumbnail 72px, chip max-width 180px** — proportional/content constraints, not spacing tokens (same category as Phase 2's 85% bubble max-width exception).

## Color

Identical palette to `03-UI-SPEC.md` — no new hues introduced:

| Role | Value | Usage |
|---|---|---|
| Surface | `hsl(var(--background))`, `hsl(var(--card))` | chip pill icon slot background (`bg-card`), toast surface (`bg-card`) |
| Secondary | `hsl(var(--muted))` | chip pill fill (`bg-muted`), generic file icon color context |
| Primary | `hsl(var(--primary))` | Reserved for exactly: (1) existing uses unchanged from Phase 3 (`Siz` label, focus rings, unread rail), (2) **drag-active drop-zone overlay** border + prompt text (`border-primary`, `bg-primary/5`, `text-primary`) — transient, visible only during an active OS drag gesture over the composer |
| Destructive | `hsl(var(--destructive))` | failed-chip icon/retry text, rejection/upload-failure toasts (`border-destructive/30`), inline-image-failure toast — same reserved usage as Phase 3, extended to these new surfaces only |

Accent is **never** used for: the attach toolbar button (stays `text-muted-foreground`, ghost, matching every other toolbar icon — it is not a toggle/active-state control), idle/uploaded chip pills (neutral `bg-muted`, not primary), the file-type icons inside chips (`text-muted-foreground`).

**Distribution (60/30/10) — carried from `03-UI-SPEC.md` unchanged.** ~60% neutral surfaces (`--background` / `--card`: composer body, chip icon slots, toast surface), ~30% secondary/muted (`--muted` chip fills, `--muted-foreground` filenames, sizes, file-type icons, attach button), ~10% accent + semantic (`--primary` limited to the transient drag overlay and existing Phase 3 uses; `--destructive` limited to failed chips and error toasts). This phase adds surface area only in the 60% and 30% bands — the 10% band gains no persistent element, since the only new primary usage (drag overlay) exists solely during an active drag gesture.

| Rejection toast — total size limit | **"Toplam ek boyutu 25 MB sınırını aşıyor."** |
| Rejection toast — overflow truncation (>3 rejected files listed) | **"+{n} dosya daha"** appended after the first 3 lines |

| Size format (Turkish locale) | `<1024 B` → `"{n} B"`; `<1024² B` → `"{n} KB"` (rounded); else → `"{n,n} MB"` (one decimal, comma separator, e.g. `"2,4 MB"`) |

## Accessibility & Safety

- **Keyboard reachability:** attach button is a normal toolbar `Button` (existing Tab order, `size="toolbar"`). Chip remove buttons and the expand/collapse summary pill are native `<button>`s, individually focusable in DOM order within the `flex flex-wrap` chip container.
- **Focus restoration after chip removal:** removing a chip via its remove button moves focus to the **next** chip's remove button if one exists; else the **previous** chip's remove button; else (list now empty) to the attach toolbar button. Never leaves focus stranded on a removed DOM node.
- **Disclosure semantics:** the 3+ summary pill uses `aria-expanded` + `aria-controls` pointing at the chip list's `id`, matching the existing `linkEditorOpen`/`headingMenuOpen` pattern already in `rich-text-composer.tsx`.
- **`role="alert"` vs toast:** attachment upload failures (chip-level) keep the project's existing inline `role="alert"` convention (matches `ThreadMessage`'s failed-message pattern exactly). Only rejection summaries and inline-paste failures — both transient, non-blocking, no persistent object to point at — use the new toast surface; toast content itself carries `sonner`'s built-in `aria-live` region, no manual `role="alert"` duplication.
- **Drag feedback for non-visual users:** the `aria-live="assertive"` drag-enter announcement (§2) is the only non-visual signal for the drop-zone overlay; screen-reader users are not expected to perform drag-and-drop, so the attach button remains the primary path — this is a known drag-and-drop accessibility limitation, not unique to this phase.
- **SVG safety (D-10):** never rendered via `<object>`/`<iframe>` anywhere in the plugin; never given a thumbnail preview at all (composer chip *or* thread render) — only the neutral `ImageIcon` file-type icon. This is stricter than D-10's literal minimum (which permits `<img>`-based SVG preview as "safe") — flagged as a deliberate consistency simplification, not a contradiction: one rule ("no SVG thumbnail, anywhere") is easier to implement correctly and audit than two similar-but-different rules for composer vs thread.
- **Filenames are untrusted input:** rendered as text only (`{filename}` in JSX, never `dangerouslySetInnerHTML`) everywhere — chips, toasts, thread attachment labels.
- **Draft-dirty extension (D-18):** no new visual element — `compose.isDirty`/`activeConversation`'s existing dirty computation gains attachment-list-non-empty as an additional `true` condition; the existing `ConfirmDialog` copy ("Yazılanlar kaybolur." / "Taslak kaybolacak") already covers this without a copy change.
