# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2: Yeni Yan Görüşme Başlatma. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** The compose screen (recipient/subject/message + send), the recipient autocomplete combobox and its 4 sub-states, the discard-confirmation dialog (dirty-form back/cancel AND active-ticket-switch variants), and the minimal post-send conversation (chat) shell with its optimistic message-bubble state machine (pending/sent/failed). Full two-way thread rendering, replies, close/reopen, and read-tracking are OUT of scope — Phase 3.

**Design system status:** This is Phase 2 of a project whose visual language was already locked in Phase 1 (`.planning/phases/01-temel-ve-salt-okunur-g-r-me-listesi/01-UI-SPEC.md`, approved). Palette, type scale, spacing scale, and component convention below are **copied verbatim from that contract, not re-derived** — Phase 2 only extends the color/copy tables where this phase introduces genuinely new surfaces (chat bubble, dropdown, dialog). Any value below without a "(NEW)" annotation is a direct restatement of the Phase 1 lock, cited so planner/executor/checker don't need to cross-reference two files to get the full palette.

## Spacing Scale

Declared values (8-point scale, multiples of 4) — **identical to Phase 1**, no new base tokens introduced:

| Token | Value | Usage (Phase 1 + Phase 2 additions) |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps; gap between meta fields (`·` separators); gap between bubble text and its pending-spinner/failed-row (NEW) |
| sm | 8px | Gap between stacked form fields in compose (NEW: recipient → subject → message vertical rhythm); gap between dropdown result rows |
| md | 16px | Default: `ScreenContent` padding, row/field internal padding (`px-4 py-3`/`py-2`), gap between compose sections |
| lg | 24px | Confirm-dialog internal padding; chat screen top padding above the first bubble (NEW) |
| xl | 32px | Vertical breathing room in empty compose states (not used — Phase 2 has no empty state of its own) |
| 2xl | 48px | not used this phase |
| 3xl | 64px | not used this phase |

Exceptions:
- **Dropdown row height:** ~40px min-height (not the generic 44px touch target) — matches Phase 1's precedent of not reserving mobile touch targets in this mouse-first, always-desktop-iframe surface. Keep consistent with `ConversationRow`'s density rather than inventing a new touch-optimized size.
- **Chat bubble max-width:** 85% of `ScreenContent`'s inner width (not a spacing token — a proportional constraint so a short message doesn't stretch full-width and long messages still wrap legibly inside ~372px).
- **Unread rail (3px), inherited from Phase 1:** not used on this phase's surfaces but documented for consistency — do not reuse the 3px rail convention for the chat bubble; the bubble's own background color is its highlight mechanism (see Color).

## Typography

**Identical to Phase 1** — same 4 roles, same 2-weight budget. No new sizes/weights introduced.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px (`text-sm`) | 400 (regular) | 1.43 (20px) — field values, dropdown row text, message textarea content, bubble message text, dialog body copy |
| Label | 12px (`text-xs`) | 600 (semibold) | 1.33 (16px) — field labels, dropdown "aranıyor…"/muted email captions, chat header meta (recipient · subject), inline validation warnings |
| Heading | 16px (`text-base`) | 600 (semibold) | 1.2 — `ScreenTitle` ("Yeni Görüşme" / chat header title), confirm-dialog title |
| Display | 18px (`text-lg`) | 600 (semibold) | 1.2 — not used this phase (no empty/hero state introduced) |

Weights used: **400 and 600 only** — same budget as Phase 1, no exception needed.

Recipient email strings (in dropdown rows and chat header) render in `font-mono` at Label size, consistent with Phase 1's `ConversationRow` treatment of `row.recipientEmail`.

## Color

**Base palette identical to Phase 1** (`hsl` values read directly from `src/index.css`):

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `hsl(210 40% 98%)` (`--background`, slate-50) | `Screen` background for compose screen and chat screen (unchanged — `Screen` component already applies `bg-slate-50` globally) |
| Secondary (30%) | `hsl(0 0% 100%)` (`--card`, white) | `ScreenHeader` bar, form field surfaces (`Input`/`Textarea` backgrounds are transparent-on-white per existing `input.tsx`), dropdown result panel, confirm-dialog card |
| Accent (10%) | `hsl(272 53% 37%)` (`--primary`, mor) | Reserved for exactly: (1) **"Gönder" button** (solid primary, `default` Button variant — the enabled equivalent of the "+" CTA this phase unlocks), (2) **free-email "kullan" row** — envelope icon + "adresini kullan" text rendered in primary to visually separate it from data rows below the search results, (3) **the sent-message bubble background** (NEW — `bg-primary text-primary-foreground`, the single largest new use of accent this phase; justified because the bubble is a small, contained element, not a screen-dominating surface, and the primary-solid-for-"your own message" pattern is the established messaging-app convention D-14 explicitly asks for), (4) the list header "+" button and empty-state CTA icon **once enabled** (same button, same color, D-01 — no new color, just `disabled` flipping to `false`) |
| Destructive | `hsl(0 84.2% 60.2%)` (`--destructive`) | Reserved for: (1) invalid-email inline warning icon + text, (2) failed-bubble "Gönderilemedi" row (icon + text + "Tekrar dene" retry affordance, matching `ErrorCard`'s red-icon-plus-Turkish-copy pattern), (3) the destructive action in both confirm-dialog variants ("Vazgeç" button, `variant="destructive"`) |

Accent is **never** used for: dropdown result row backgrounds, subject/recipient input borders in their default state, the incoming-message bubble that Phase 3 will add (that variant must use Secondary/white, not primary — noted here so Phase 3 doesn't accidentally reach for primary on both sides of a thread).

### Bubble state colors (supplementary — not part of the 60/30/10 split, same rationale as Phase 1's badge-color table)

| State | Background | Foreground/Icon | Usage |
|-------|-----------|------------------|-------|
| Pending (optimistic) | `bg-primary` | `text-primary-foreground`; small `ReloadIcon` (`animate-spin`, ~12px, `text-primary-foreground/70`) bottom-right inside bubble padding | POST in flight — D-14 |
| Sent (resolved) | `bg-primary` | `text-primary-foreground`, no spinner (bubble simply stops showing the spinner — no separate checkmark icon needed, keeps the icon budget minimal) | POST 2xx resolved |
| Failed | `bg-primary` (message text stays, per D-15 — do not recolor the bubble itself to red) | Below the bubble text, inside the same bubble container: `ExclamationTriangleIcon` (`text-destructive-foreground` or `text-red-200` depending on contrast against `bg-primary` — executor picks whichever passes AA against primary) + "Gönderilemedi · Tekrar dene" as a tappable inline action | POST rejected/network error — D-15 |

**Assumption:** D-15's literal copy has a "⚠" glyph prefix; this contract replaces the emoji glyph with `ExclamationTriangleIcon` (component, not Unicode character) to match the existing icon-driven convention already used in `error-card.tsx` and the Envelope row above — Phase 1 never renders raw emoji anywhere in the codebase, so Phase 2 shouldn't introduce the first one.

## Layout & Component Notes

*(Supplementary section — not part of the template's fixed schema, carried over from Phase 1's precedent because this phase's screen anatomy and state machines are load-bearing for planner/executor.)*

### New components needed this phase

| Component | New/Existing | Notes |
|-----------|--------------|-------|
| `Textarea` | New | Same visual language as `input.tsx` (border, `rounded-md`, `shadow-sm`, `focus-visible:ring-1`, `disabled:opacity-50`) but multi-line: no fixed height, `min-h-[96px]` (~4-5 lines), grows with content up to a reasonable cap, then scrolls internally. `cva`+`cn`, forwardRef, same prop-spreading pattern as `Input`. |
| `ComposeScreen` | New | `Screen`/`ScreenHeader` (`onBack`, title "Yeni Görüşme")/`ScreenContent` — reuses Phase 1's screen-swap pattern exactly, no router, no modal. |
| `RecipientField` (combobox) | New | `Input` + an absolutely-positioned dropdown panel below it (`bg-card`, `shadow`, `rounded-md`, `border`). See "Recipient dropdown states" below. |
| `SubjectField` | New | Plain `Input`, prefilled, editable; empty-state inline warning text below (non-blocking). |
| `MessageField` | New | `Textarea` + persistent keyboard-hint caption below it. |
| `ConfirmDialog` | New | Small centered modal: `fixed inset-0 bg-black/40` overlay + centered `bg-card rounded-lg shadow-lg p-6` card (title, body, two right-aligned buttons). Used for both D-02 and D-03 variants (same component, different copy/props — do not build two separate dialogs). |
| `ChatScreen` (minimal shell) | New | `Screen`/`ScreenHeader` (`onBack` → list)/`ScreenContent` containing exactly one `MessageBubble` (own-message variant) this phase. Built as the extension point Phase 3 hangs its full thread (list of bubbles, both directions, reply composer) off of — keep the bubble list container generic (e.g., a simple vertical flex list) rather than hardcoding "exactly one child." |
| `MessageBubble` | New | Own-message variant only this phase (right-aligned, `bg-primary`, max-width 85%, `rounded-lg` with a tighter corner on the sender's side e.g. `rounded-br-sm`). State machine: pending → sent → failed (see Color table). Phase 3 will add an incoming-message variant (left-aligned, `bg-card`/white, bordered) — do not couple this component so tightly to "always primary/right" that adding that variant requires a rewrite; a `variant`/`direction` prop is the natural seam. |

### Recipient dropdown states (D-04, D-05, D-06)

1. **Idle** — input empty or <3 chars: no panel rendered.
2. **Loading** — 3+ chars, debounce (~300ms) elapsed, request in flight: panel shows "Aranıyor…" (muted, centered, Label size).
3. **Results** — customer rows, each: name (Body, 400) + email (Label, muted, `font-mono`) stacked, or email-only (Label, `font-mono`) if no name on the record (planner's fallback discretion per CONTEXT.md). Rows are keyboard-navigable (arrow keys + Enter) as a baseline a11y expectation for a combobox, even though CONTEXT.md doesn't spell this out explicitly.
4. **Free-email row** — appended below results (or shown alone if zero customer matches) only when typed text passes email-format validation: distinct via the primary-colored `EnvelopeClosedIcon` + text and a `border-t` divider separating it from data rows above.
5. **Invalid-email / no-match** — typed text fails email-format validation and matches no customers: "Geçerli bir e-posta adresi girin." inline warning under the input (destructive-colored, Label size); no free-email row; "Gönder" disabled.

### Compose screen anatomy (top to bottom, `ScreenContent`, `md` 16px gaps)

1. `RecipientField` (with its dropdown, D-04..D-07)
2. `SubjectField` (prefilled, D-08/D-09)
3. `MessageField` (textarea + keyboard hint, D-10..D-12)
4. **"Gönder" button** — full-width, `default` (primary) variant, pinned as a bottom action bar (`border-t`, `bg-card`, sticky within the screen) rather than scrolling away with the textarea, so it stays reachable as the message grows. This mirrors `ScreenHeader`'s existing pattern of a fixed chrome element inside an otherwise-scrolling `Screen`.

### Chat screen anatomy (minimal shell, D-14)

`ScreenHeader` (`onBack` → list, title = "{recipient} · {subject}", truncated) → `ScreenContent` with `lg` (24px) top padding, then a single right-aligned `MessageBubble` in its `pending` state immediately on mount (optimistic), transitioning to `sent` or `failed` when the `createTicket`/comment POST settles.

### Screen flow / state machine (no router — same pattern as Phase 1)

`List` → ("+"/empty-CTA, now enabled) → `Compose` → (valid submit) → `Chat` (bubble: `pending` → `sent` | `failed`, retry re-POSTs without leaving `Chat`) → (back arrow) → `List` (refetched per SYNC-02/D-16, not an optimistic fake row).

Dirty-exit paths: `Compose` → (back/cancel while dirty) → `ConfirmDialog` (D-02 copy) → confirmed → `List`; unconfirmed → stays on `Compose`. `Compose` → (active ticket changes while dirty) → `ConfirmDialog` (D-03 copy) → confirmed → `Compose` closes, new ticket's `List` loads; unconfirmed → stays on `Compose` for the original ticket.

### Panel width constraint

Unchanged from Phase 1: everything fits inside ~372px, no horizontal scroll. Dropdown panel width matches its trigger input's width exactly (no overflow beyond the field). Bubble max-width (85%) and `line-clamp`/`truncate` on header meta text are this phase's mechanisms for the same constraint.
