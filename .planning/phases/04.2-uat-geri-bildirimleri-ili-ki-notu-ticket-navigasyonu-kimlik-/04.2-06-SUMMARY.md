# Phase 04.2 Plan 06: Chat screen — header, recipient, identity and info-box wiring Summary

**The chat screen header now composes `TicketKeyLink` (side ticket, purple link) and `ParentKeyChip` (parent ticket, neutral chip) instead of showing the recipient; the recipient reappears as a defensive `Alıcı:` line in the solved/closed block so it's visible in every reachable state; `ThreadMessage` receives real `agentEmail`/`agentName` so the `Siz` badge and pending-message sender name resolve; and a session-scoped, once-only `InfoBox` now informs the agent right after creating a new side conversation.**

## Accomplishments

- **Task 1 — header composition (D-06/D-07/D-08/D-10):** `ScreenHeader`'s `title` renders `TicketKeyLink` only when `sideKey`, `tenantId`, and `environment` are all resolved; otherwise a plain-text placeholder (`sideKey` itself if known, else `"Yeni konuşma"`) — never a partial/broken link. `subtitle` composes `ParentKeyChip` (compact, only when `parentKey` exists) ahead of the existing `"Konu: …"` text, which stays the only truncating element in that row. `recipientLabel` is fully removed from the header. `ScreenHeader`/`ScreenTitle`/`screen.tsx` are untouched — composition happens entirely at the call site via the existing `ReactNode` `title`/`subtitle` props.
- **Task 2 — recipient defense + identity wiring (D-09/D-13/D-14):** The solved/closed status block gains a defensive `Alıcı: {recipientLabel}` paragraph, rendered only when the label is non-empty (never a placeholder dash). `ThreadMessage` now receives `agentEmail={agentEmail}` and `agentName={agentName}` from `useGrispi()`, closing the gap Plan 03 left open — the `Siz` badge and the pending-optimistic-message name fallback are now provably correct at the screen level.
- **Task 3 — one-time dismissible info box (D-16b):** A `useRef`-tracked `sessionKey` + `useState` boolean latch distinguishes conversations created in this session (pending create → bound ticket) from conversations opened from the list, entirely as local presentation state (no `PanelNavigationStore` changes). `InfoBox` renders as `ScreenContent`'s first child, above the `solved`/`lifecycleError` bands, gated by tenant + not-yet-seen + created-this-session. Dismiss calls `setInfoBoxSeen(tenantId)`, hides the box, and moves focus to the header's back button via a `display:contents` wrapper ref (since `Screen`/`ScreenHeader` are plain function components with no `forwardRef`, and `screen.tsx` may not be modified).

## Decisions Made

- Header title falls back to `sideKey` as plain text (not just `"Yeni konuşma"`) when `sideKey` is present but `tenantId`/`environment` isn't yet resolved — the UI-SPEC's example only covers the `sideKey === null` pending-create case; extending the same "never a broken link, always something readable" principle to the bootstrap-incomplete edge case is a straightforward, low-risk extrapolation of the same rule.
- Post-dismiss focus transfer uses a `display:contents` wrapper `<div ref={screenRootRef}>` around `<Screen>` rather than adding a new prop to `ScreenHeader` — required because `Screen`/`ScreenHeader` are plain `FC`s (not `forwardRef`) and `screen.tsx` is explicitly prohibited from modification by this plan.
- The "created this session" latch is implemented entirely as chat-screen-local state (a `useRef` tracking which `sessionKey` the latch was last evaluated for, plus a `useState` boolean), not as a `PanelNavigationStore` addition — it's a pure derived presentation fact (sideKey starts `null` only on the create path) and doesn't need to survive outside this component's lifetime.
- The `InfoBox` render condition explicitly ANDs `tenantId`, `infoBoxVisible`, and `createdThisSession` even though `infoBoxVisible`'s own initializer already implies `tenantId` truthy — kept as three explicit terms as instructed by the plan, as a defensive guard against a future refactor of `infoBoxVisible`'s initializer silently dropping the tenant check.

### Process deviation (documented, not a Rule 1-4 case)

**1. Single commit instead of one commit per task**
- **What happened:** All three tasks share the identical `<files>` list (`chat-screen.tsx`, `chat-screen.test.tsx`) and touch overlapping regions of the same `return` JSX block (Task 2's `ThreadMessage` prop wiring sits inside the same message-feed block Task 3's `InfoBox` sits just above). The three tasks were implemented together in a single edit pass and verified together with one full `craco test --testPathPattern=chat-screen` run (27/27 passing) before any commit was made.
- **Why not split after the fact:** The standard recovery for this — resetting the files to their pre-plan state via `git checkout -- <file>` and re-applying each task's slice of the diff in three stages — was attempted and blocked by the environment's permission classifier (a sanctioned, non-destructive use of `git checkout -- <specific file>` per this workflow's own destructive-git-prohibition carve-out was still refused). Re-deriving three clean, independently-buildable hunks from the final interleaved diff via manual patch construction was assessed as higher-risk (risk of a broken intermediate commit state) than documenting the deviation.
- **Impact:** None on functionality, test coverage, or the final code — all three tasks' behavior is independently covered by dedicated test `describe` blocks and independently verifiable via the plan's `<acceptance_criteria>` grep gates (all pass, see below). The only effect is coarser git history granularity for this one plan.

### Known pre-existing gate mismatches (not deviations, not fixed)

Two of the plan's literal `grep -c` acceptance counts don't match the live file because the planner's count didn't anticipate that `info-box-store.ts`'s own exported function names (`getInfoBoxSeen`/`setInfoBoxSeen`) and this screen's local identifiers (`infoBoxVisible`, `handleDismissInfoBox`) all legitimately contain the substring `"InfoBox"`/`"InfoBoxSeen"` — the same category of cosmetic miscount Plan 01 and Plan 02 both documented for their own doc-comment/naming collisions:

- `grep -c "InfoBox" src/screens/chat-screen.tsx` → `9` (plan expected `2`, i.e. import + one JSX usage). The extra 7 matches are the `info-box-store` import line, the `infoBoxVisible` state declaration and its two reads, and the `handleDismissInfoBox` function's declaration and one call site — all necessary, correctly-named identifiers, not duplicate imports or duplicate renders.
- `grep -c "setInfoBoxSeen" src/screens/chat-screen.tsx` → `2` (plan expected `1`). One match is the named import (`import { getInfoBoxSeen, setInfoBoxSeen } from "@/lib/info-box-store"`), the other is the actual call site inside `handleDismissInfoBox`. A function that is imported AND called will always produce at least 2 line-matches for its own name under a literal `grep -c`; there is no naming scheme that reduces this to 1 without either omitting the import (impossible) or renaming the call site to something misleading.

Both are cosmetic grep-gate miscounts in the plan, not defects — the underlying behavior (the info box renders/hides/dismisses correctly, calling `setInfoBoxSeen` exactly once per dismiss) is independently confirmed by 5 passing dedicated tests and the full 494/494 suite.
