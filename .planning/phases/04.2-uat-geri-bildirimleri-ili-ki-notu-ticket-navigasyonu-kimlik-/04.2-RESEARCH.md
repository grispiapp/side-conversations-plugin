# Phase 04.2: UAT geri bildirimleri — Research

**Researched:** 2026-08-17
**Domain:** Live Grispi API contract verification (internal-note PATCH) + in-repo UI/state remediation (identity clarity, ticket navigation, narrow/short-panel resilience)
**Confidence:** HIGH

## Summary

This phase closes ten live-UAT feedback items with **zero new libraries and zero new API capabilities beyond one PATCH shape**. The single open technical risk named in CONTEXT.md — whether `PATCH /v2/tickets/{key}` with `comment.publicVisible: false` sends no email and leaves `ts.status` untouched — was verified live against `gsocial-test` this session and **CONFIRMED**: D-01's create-then-PATCH ordering is safe to plan as written, no reversal needed.

Beyond the required probe, three additional live/code findings materially change what the planner needs to know: (1) the preprod agent-UI TLD (`grispi.net`) is confirmed live, but the `GrispiEnvironment` value needed to build that URL is **not currently exposed** anywhere in `GrispiContextType` — a new piece of threaded state, not just a new component, is required for D-07/UX-02; (2) `switchTicket`'s provisional `{ key }` ticket object has no `fieldMap`, so D-11's parent-detection read (`ticket.fieldMap["tu.side_conversation_parent"]?.value`) will silently evaluate to `undefined` for one hydration round-trip — the safe failure mode (banner absent, not wrong-banner), but it means the "block new side conversation" guard must key off hydration completeness, not `ticket !== null`; (3) a reproducible, previously undocumented anomaly was found where `POST /v2/tickets`'s `fields` array does not immediately persist a custom `TEXT` field (`tu.side_conversation_parent`) on two independent fresh creates, while a same-key `PATCH public/v1/tickets/{key}` with only `fields` persists it instantly — flagged as an out-of-scope but relevant production-reliability observation, not a Phase 04.2 fix target.

For the UI work: no Radix Popover/Dropdown primitive is installed, and none is needed — this codebase already has a fully accessible hand-rolled `role="menu"` popover pattern in `chat-screen.tsx` (outside-click, Escape, Tab-close, focus-return) that should be copied for the D-18 "Aa" formatting popover rather than adding a dependency. The short-viewport (D-19) and narrow-width (D-20) work is almost entirely CSS/JSX — the token layer (`--panel-header-height`, `--panel-inset`, `--interactive-target`) is `.dark`-independent (colors only), so a `@media (max-height: 620px)` block can safely override the three layout tokens without touching `.dark`; three hardcoded heights (`min-h-[72px]` ×2 in `conversation-row.tsx`, `min-h-48`/`max-h-40 min-h-24` in `rich-text-composer.tsx`) do NOT respond to token changes and need their own compact-mode class.

**Primary recommendation:** Plan D-01 as specified (create public comment → await a second PATCH with `publicVisible: false`, 1 retry, silent `console.error` on failure) but sequence the PATCH to complete **before** `executeCreateMutation`'s existing `refreshCanonicalAfterMutation` refetch — otherwise the agent's first view of the new conversation can race ahead of the internal note and miss it until the next poll.

## Live API Probe Results (gsocial-test, preprod)

All calls made against `https://api.grispi.net` using the dev bearer token from `.env.development.local` (never logged/printed). Probe artifacts created in the tenant (no PII): `TICKET-601`, `TICKET-602` (both children of `TICKET-563`, subject prefixed `[TEST-PROBE 04.2]`, safe to ignore/leave).

### P1 — Does `publicVisible: false` avoid email + leave `ts.status` unchanged? **CONFIRMED**

`[VERIFIED: live API probe — gsocial-test, this session]`

Created `TICKET-601` via `POST /v2/tickets` (public comment, `ts.status` → `1` "New"), then issued:

```
PATCH https://api.grispi.net/v2/tickets/TICKET-601
{
  "comment": {
    "body": "…internal note text…",
    "publicVisible": false,
    "creator": [{"key":"us.email","value":"<agent email>"}],
    "channel": "WEB"
  }
}
```

Result: **HTTP 200**, `ts.status` remained `"1"` ("New") — completely unchanged. Response comment object carries no separate "sent" indicator, but the follow-up `GET` (P3) is decisive:

- The internal-note comment round-trips with **`"toId": null, "toEmail": null`** — no recipient was ever attached to this comment, which is the server-side signature of "no outbound delivery target exists." Contrast with the public create comment in the same response, which shows `"toId": 128, "toEmail": "test-probe-0817@example.com"`.
- This corroborates an existing independent finding from Phase 1's live probe (`01-02-probe-findings.md` #6): *"`publicVisible` spec açıklaması TERS: canlı davranış `true` = public yorum, `false` = dahili not (oluşturma ve görüntülemede tutarlı)."* Two independent live probes, five weeks apart, agree.
- No mailbox-level (actual inbox) confirmation was performed — consistent with this project's existing "P6b" pattern (Phase 4), where transport-level proof is accepted as sufficient and full mailbox inspection is deferred to human UAT. Flag this the same way in the phase's UAT checklist.

**Verdict: D-01's create-then-PATCH ordering is safe. No reversal to the create-with-internal-note-first fallback is needed.**

### P2 — Does the PATCH succeed at all with `publicVisible: false`? **CONFIRMED — 200, no rejection**

`[VERIFIED: live API probe — gsocial-test, this session]`

No validation error, no 4xx/5xx. The exact response shape is the same mutation-ticket-object shape `Tickets.replyTicket` already receives (`PatchTicketResponse` — matches the existing type, no new type needed for the response side). Only the **request** side needs a new type, since `ReplyTicketPatchRequest.comment.publicVisible` is deliberately narrowed to the `true` literal in `src/types/grispi.type.ts` (by design, to prevent `replyTicket` from ever silently going internal). **Recommendation: add a sibling type (e.g. `InternalNotePatchRequest`) and a new `Tickets.addInternalNote(ticketKey, body, agentEmail)` client method** — do not widen `ReplyTicketPatchRequest` or reuse `replyTicket`, that would defeat the exact type-safety guarantee the codebase already relies on elsewhere (`StatusTicketPatchRequest`'s locked tuple, `CreateTicketRequest.publicVisible: true` literal — this is an established pattern in this codebase, not a one-off).

### Adjacent finding (not one of P1–P4, discovered during setup) — `POST /v2/tickets` custom-field write anomaly

`[VERIFIED: live API probe — gsocial-test, this session]` — **out of scope for this phase, documented for awareness only**

Two independent fresh creates (`TICKET-601`, `TICKET-602`), each via `POST /v2/tickets` with a `fields` array including `{"key":"tu.side_conversation_parent","value":"TICKET-563"}` (exact production shape, including the correct `formatRequesterField`-style `:email` prefix for `ts.requester` on the second attempt), left `tu.side_conversation_parent` reading back as `null` on **both** the create response's own `fieldMap` and a subsequent direct `GET public/v1/tickets/{key}` — persisting for 10+ minutes (ruled out as search-index lag, since `GET` reads the primary record, not the search index; `totalSize` in `advanced-search` also did not include the new ticket after the same delay). A **separate immediate `PATCH public/v1/tickets/{key}` with only `{"fields":[{"key":"tu.side_conversation_parent","value":"TICKET-563"}]}`** persisted the value instantly and correctly (confirmed via immediate re-`GET`).

This is unrelated to any of Phase 04.2's locked decisions (D-01 through D-21) and is **not** recommended as an in-scope fix — it would be scope creep on a UAT-feedback phase. It is noted here because:
1. It is the exact mechanism D-11 (UX-03) reads (`tu.side_conversation_parent`) to detect "this ticket IS a side conversation" — if this anomaly is ever hit in the wild (agent navigates the host Grispi tab to a side ticket within seconds of its creation), D-11's banner would correctly fail *closed* (absent, not wrong), matching the same safe-default already required for the hydration-flash risk below.
2. Existing production side tickets (e.g. `TICKET-591`, confirmed live in this session) do NOT exhibit this — their `tu.side_conversation_parent` reads back correctly — so this is not a regression affecting shipped functionality, only an observed edge case on freshly-created tickets within the first several minutes.
3. If a fix is ever wanted, the mechanism is already proven: a follow-up `fields`-only `PATCH public/v1/tickets/{key}` — structurally the exact same "create, then PATCH a correction" pattern D-01 already establishes for the internal note. Worth a `Pending Todos` capture, not a Phase 04.2 task.

## Architecture Patterns

### System Architecture Diagram — D-01 internal-note sequencing (the one new write path)

```
Agent submits new side conversation (ComposeScreen.submit)
        │
        ▼
ComposeStore.submit() builds CreateTicketRequest
        │
        ▼
ActiveConversationStore.startNew() → optimistic pending bubble
        │ (fire-and-forget from UI's perspective)
        ▼
executeCreateMutation(queryClient, boundary, envelope)
        │
        ├─► POST /v2/tickets  (public comment, publicVisible:true) ──► sideKey
        │
        ├─► boundary.bindCreatedTicket(sessionKey, sideKey)
        │
        ├─► ★ NEW: PATCH /v2/tickets/{sideKey}                          ★
        │      { comment: { body: D-02 text, publicVisible:false,      ★
        │                    creator:[{key:"us.email",value:agentEmail}]}}★
        │      — awaited, wrapped in its own try/catch (D-04: 1 retry,  ★
        │        then console.error only — NEVER throws out of this    ★
        │        function, NEVER blocks/fails the create envelope)     ★
        │      — MUST complete (success or exhausted-retry) BEFORE the ★
        │        next step, so the note is present in the same refetch ★
        │
        ▼
refreshCanonicalAfterMutation() — invalidates list, refetches detail,
        reconciles canonical messages (ALREADY EXISTS, unchanged)
        │
        ▼
Agent opens chat screen → sees BOTH comments in one render
        (public comment + internal note, via UNCHANGED normalizeComment/
         ThreadMessage — internal-note rendering requires zero new
         components, only D-15's label text edit)
```

**Why the PATCH must be awaited before `refreshCanonicalAfterMutation`, not truly fire-and-forget:** the existing `refreshCanonicalAfterMutation` performs exactly one detail refetch after the mutation settles. If the internal-note PATCH is dispatched without being awaited (genuinely "fire and forget"), it races the refetch — most of the time it will lose, and the agent's first view of the new conversation will be missing the internal note until the *next* independent refetch (a manual reopen, or the next 15s `DETAIL_STALE_TIME` window). D-04's "no toast, no blocking of the agent's own action" requirement is satisfied by keeping the PATCH failure silent (console.error only) and never rejecting the outer promise — it does NOT require skipping the `await`. Await it, swallow its errors internally, then proceed to the existing refresh call unchanged.

### Pattern 1: Threading the resolved `GrispiEnvironment` to components (new — required for D-07/UX-02)

**What:** `GrispiContextType` currently exposes `ticket`, `tenantId`, `settings`, `loading`, `agentEmail`, `standalone`, `switchTicket` — no `environment`. `HttpHandler.setEnvironment(environment)` immediately converts the enum key into a base-URL *string* and discards the key; `GrispiAPI` has no public getter for it either (`httpHandler` is `private`).

**When to use:** Any time a component needs to build an environment-dependent URL that is NOT an API call (i.e., the agent-UI ticket link, D-07) — API calls never need this, they go through `grispiAPI`'s already-configured `baseUrl`.

**Example — mirrors the existing `agentEmail` threading exactly:**
```typescript
// Source: src/contexts/plugin-bootstrap.ts + grispi-context.tsx (existing pattern, this repo)
// 1. grispi-context.tsx: add environment to state + context value
const [environment, setEnvironmentState] = useState<GrispiEnvironment | null>(null);
// ...
value={{ ticket, tenantId, settings, loading, agentEmail, environment, standalone, switchTicket }}

// 2. plugin-bootstrap.ts: BootstrapPluginInitDeps gains a parallel setter,
//    called at the SAME call site as the existing setEnvironment (HttpHandler)
//    call — do not replace it, add alongside it:
deps.setEnvironment(resolveGrispiEnvironment(bundle.settings, bundle.context.token)); // existing (HttpHandler)
deps.setEnvironmentState(resolveGrispiEnvironment(bundle.settings, bundle.context.token)); // NEW (React state)

// 3. environment.ts: derive TLD from the SAME canonical map, no new literal
export function grispiTld(env: GrispiEnvironment): string {
  return GRISPI_BASE_URLS[env].replace(/^https:\/\/api\.grispi\./, "");
}
export function buildAgentTicketUrl(
  tenantId: string,
  env: GrispiEnvironment,
  ticketKey: string
): string {
  return `https://${tenantId}.grispi.${grispiTld(env)}/tickets/${encodeURIComponent(ticketKey)}`;
}
```
Both `grispiTld`/`buildAgentTicketUrl` belong in `src/grispi/client/environment.ts` per CORE-04's canonical-home rule (04.1-01 threat model), not in a new file.

**Standalone-dev mode:** already resolves `environment: GrispiEnvironment` in `standalone-dev.ts`'s `StandaloneDevConfig` — the same `setEnvironmentState` call must be added to `grispi-context.tsx`'s standalone branch (line ~163, alongside the existing `grispiAPI.setEnvironment(standaloneConfig.environment)`).

### Pattern 2: D-11 hydration-flash guard (new — required for UX-03)

**What:** `switchTicket` (grispi-context.tsx) sets `setTicket({ key: ticketKey } as Ticket)` synchronously (no `fieldMap`), THEN awaits `getTicket` and replaces it with the full hydrated object. Any code reading `ticket.fieldMap?.["tu.side_conversation_parent"]?.value` during that window gets `undefined` (optional chaining degrades safely — `undefined`, not a throw).

**When to use:** Anywhere D-11's "is the active ticket itself a side conversation" check is computed — the ParentBanner's visibility AND the "block new side conversation" guard on `PanelNavigationStore.openCompose()`.

**The risk is NOT "wrong banner shown"** (a falsy read during the flash just means the banner is momentarily absent — the safe direction). **The risk is the guard silently NOT blocking `openCompose()`** during that same window, since `undefined` also fails the "is a side conversation" check. A fast-clicking agent on a just-switched ticket could, in principle, open compose during the ~1 API round-trip before `fieldMap` exists.

**How to avoid it:** Gate `openCompose()`'s parent-check (and the banner) on hydration completeness, not just `ticket !== null`. The cheapest correct signal already in the codebase: `"fieldMap" in ticket` (the provisional object never has this key; every hydrated `Ticket` always does, even with a null-valued field). Do not introduce a separate `hydrating` boolean in context — reuse the shape difference that already exists.

```typescript
// Recommended predicate — Source: src/contexts/grispi-context.tsx (switchTicket) read this session
function isHydrated(ticket: Ticket | null): ticket is Ticket {
  return ticket !== null && "fieldMap" in ticket;
}
const isSideConversation =
  isHydrated(ticket) &&
  Boolean(ticket.fieldMap[SIDE_CONVERSATION_PARENT_FIELD_KEY]?.value);
```

### Pattern 3: Hand-rolled accessible popover (reuse for D-18/UX-07)

**What:** `chat-screen.tsx`'s "…" conversation-options menu (lines ~296–363) is a complete, tested, accessible popover: trigger `<Button aria-haspopup="menu" aria-expanded>`, `role="menu"` panel, `mousedown` outside-click close, `Escape`/`Tab` close, `onBlur` relatedTarget check, focus-first-item on open, focus-return-to-trigger on close.

**When to use:** The D-18 "Aa ▾" formatting popover in `rich-text-composer.tsx` — same shape of problem (button-triggered panel of grouped actions, must not steal focus from the editor unexpectedly, must close on outside interaction).

**Why not the existing inline heading-menu/link-editor panels already in `rich-text-composer.tsx`:** those are *docked* panels (render inline below the toolbar row, shift layout), not floating popovers — acceptable for the current heading/link editors but wrong shape for D-18, which needs a compact overlay so the toolbar row itself shrinks (the whole point of consolidating 6 formatting buttons behind one trigger is to reclaim horizontal space at ~280px). The `menuRef`/`menuTriggerRef`/outside-click/Escape logic from `chat-screen.tsx` is what to copy; the *rendering* (absolute-positioned overlay near the trigger, not a full-width docked row) should follow UI-SPEC discretion, not the heading-menu's docked pattern.

**Example:**
```typescript
// Source: src/screens/chat-screen.tsx lines 118-153 (existing, this repo) — copy this exact
// outside-click/Escape/focus-return shape for the Aa popover's open/close lifecycle.
const closeMenu = useCallback((returnFocus = true) => {
  setMenuOpen(false);
  if (returnFocus) menuTriggerRef.current?.focus();
}, []);

useEffect(() => {
  if (!menuOpen) return;
  menuItemRef.current?.focus();
  const handlePointerDown = (event: MouseEvent) => {
    const target = event.target as Node;
    if (menuRef.current?.contains(target) || menuTriggerRef.current?.contains(target)) return;
    closeMenu();
  };
  const handleKeyDown = (event: globalThis.KeyboardEvent) => {
    if (event.key === "Escape") { event.preventDefault(); closeMenu(); }
    else if (event.key === "Tab") { closeMenu(false); }
  };
  document.addEventListener("mousedown", handlePointerDown);
  document.addEventListener("keydown", handleKeyDown);
  return () => {
    document.removeEventListener("mousedown", handlePointerDown);
    document.removeEventListener("keydown", handleKeyDown);
  };
}, [closeMenu, menuOpen]);
```

## Common Pitfalls

### Pitfall 1: Racing the internal-note PATCH against the existing detail refetch
**What goes wrong:** The internal note is created successfully server-side, but the agent's chat screen doesn't show it on first open.
**Why it happens:** `executeCreateMutation`'s `refreshCanonicalAfterMutation` already refetches ticket detail once, right after create. If the internal-note PATCH is truly "fire and forget" (not awaited before that refetch), the refetch usually wins the race.
**How to avoid:** `await` the PATCH (internally, with its own try/catch — D-04's "no toast/no blocking" is about UI surfacing, not about skipping the await) before calling `refreshCanonicalAfterMutation`.
**Warning signs:** UAT report "the internal note only shows up after I close and reopen the conversation."

### Pitfall 2: Reading `ticket.fieldMap` during the provisional-ticket window
**What goes wrong:** D-11's "block new side conversation" guard doesn't block during the instant after a ticket switch, before hydration completes.
**Why it happens:** `switchTicket` sets a keys-only provisional ticket synchronously; `fieldMap` is `undefined` until `getTicket` resolves.
**How to avoid:** Use the `isHydrated()` predicate (Pattern 2), not a bare `ticket !== null` check, anywhere D-11's parent-detection matters.
**Warning signs:** Intermittent, hard-to-reproduce reports of "I was able to start a new side conversation from inside a side conversation" — only reproducible on a fast double-click right after switching tickets.

### Pitfall 3: Reusing `ReplyTicketPatchRequest`'s type for the internal note
**What goes wrong:** Either a TypeScript error (the type literal-narrows `publicVisible` to `true`), or — if "fixed" by widening that type to `boolean` — a class of bug where `replyTicket` (the public-reply path) could theoretically be called with `publicVisible: false` by a future caller, silently turning a real reply into a hidden internal note.
**Why it happens:** Surface-level, `ReplyTicketPatchRequest` "looks like" the right shape to reuse.
**How to avoid:** Add a sibling type (`InternalNotePatchRequest`) and a dedicated `Tickets.addInternalNote()` method (P2 finding above). This mirrors the codebase's own established pattern (`StatusTicketPatchRequest`'s locked tuple, `CreateTicketRequest.publicVisible: true` literal) of using TypeScript literal narrowing as a load-bearing safety mechanism, not just documentation.
**Warning signs:** A type error at the call site is actually the GOOD outcome here — it means the guard is working. Don't "fix" it by widening the existing type.

### Pitfall 4: Assuming the `.dark` block conflicts with a `@media (max-height:)` token override
**What goes wrong:** Hesitating to add a `@media (max-height: 620px)` block inside `@layer base` out of concern it will fight `.dark`'s selector specificity.
**Why it happens:** Surface-level pattern-matching ("there's already a conditional variant block, adding another might collide").
**How to avoid:** `.dark` only overrides *color* tokens (`--background`, `--foreground`, `--primary`, etc.) — it never touches `--panel-header-height`, `--panel-inset`, or `--interactive-target`. A `@media (max-height: 620px) { :root { --panel-header-height: …; --panel-inset: …; --interactive-target: …; } }` block is orthogonal (different tokens, different at-rule) and needs no `.dark`-specific handling at all — this plugin is documented as "always-light-theme" anyway (`.claude/CLAUDE.md`: "her zaman açık tema").
**Warning signs:** None expected if the above is followed; this is a preemptive note, not an observed bug.

### Pitfall 5: Forgetting the two hardcoded heights that don't respond to token changes
**What goes wrong:** D-19's token override ships, but `conversation-row.tsx` rows and the reply composer's editor area don't actually get shorter/taller at `max-height: 620px`.
**Why it happens:** `min-h-[72px]` (both `ConversationRow` and `SkeletonRow` in `conversation-row.tsx`) and `min-h-48` / `max-h-40 min-h-24` (`editorClassName` in `rich-text-composer.tsx`) are literal Tailwind arbitrary-value classes, not `var(--…)` references — a `:root` custom-property override cannot touch them.
**How to avoid:** These need their own compact-mode class, gated the same way (either a `useMediaQuery`-style hook reading `(max-height: 620px)`, or — simpler, matching this codebase's CSS-first approach elsewhere — a Tailwind `max-h-[620px]:` arbitrary-variant equivalent is not standard Tailwind 3 syntax; the pragmatic option is a small custom utility class defined in `index.css`'s own `@media (max-height: 620px)` block, e.g. `.conversation-row-compact { min-height: 56px; }`, applied via `cn()` conditionally is unnecessary if it's pure CSS — prefer defining the override as a plain CSS rule scoped by the SAME media query, targeting the existing class names directly (`@media (max-height: 620px) { .rich-text-content-editor-compose { min-height: …; } }`), which requires zero JS/React changes, only a stable class name to hook the CSS selector onto (already present as Tailwind-generated utility classes, or add one explicit marker class per D-19 target if the Tailwind-generated class isn't stable/selector-safe).
**Warning signs:** Live UAT at ~590px viewport height shows unchanged row/editor heights despite the media query firing (verifiable via DevTools computed-styles panel).

### D-16 info-box dismissal — exact `last-seen-store.ts` precedent to mirror
```typescript
// Source: src/lib/last-seen-store.ts (existing, this repo) — mirror this shape exactly
// for D-16(b)'s "seen once, permanently dismissed" info box, tenant-scoped (not
// ticket-scoped, since the tip is evergreen product guidance, not tied to one thread).
const KEY_PREFIX = "sc:infoBoxSeen:"; // new prefix, same namespace convention

function storageKey(tenantId: string): string {
  return `${KEY_PREFIX}${encodeURIComponent(tenantId)}`;
}

export function getInfoBoxSeen(tenantId: string): boolean {
  if (!tenantId.trim()) return false;
  try {
    return window.localStorage.getItem(storageKey(tenantId)) === "1";
  } catch {
    return false; // defensive degrade — iframe storage restrictions can throw on ACCESS, not just write
  }
}

export function setInfoBoxSeen(tenantId: string): boolean {
  if (!tenantId.trim()) return false;
  try {
    window.localStorage.setItem(storageKey(tenantId), "1");
    return true;
  } catch {
    return false;
  }
}
```

## Open Questions

1. **Should the internal-note PATCH's 1 retry (D-04) use the same retry mechanism as `ActiveConversationStore`'s existing lifecycle retry, or a fresh, local one-shot retry inline in `executeCreateMutation`?**
   - What we know: `ActiveConversationStore` already has a generation-guarded retry concept (`getRetryEnvelope`), but that's user-facing (a visible "Tekrar dene" button) — D-04 explicitly wants this invisible to the agent.
   - What's unclear: whether the planner wants a shared "retry once, then log" helper (reusable for future silent-background-write features) or an inline `try { … } catch { try { … } catch { console.error } }` — both are D-04-compliant.
   - Recommendation: inline is simpler and this is the first (and, per D-05, currently only) silent background write in the codebase — no reuse pressure yet. A shared helper is speculative generality until a second caller exists.

2. **Where exactly should `agentName` be threaded from — is `bundle.context.agent.fullName` reliably present in the standalone-dev path too?**
   - What we know: `plugin-bootstrap.ts` reads `bundle.context.agent?.email` today (optional chaining — already defensive against a missing `agent`). `standalone-dev.ts`'s `StandaloneDevConfig` has no `agentName` field, only `DEFAULT_DEV_AGENT_EMAIL`.
   - What's unclear: whether standalone mode needs a matching `DEFAULT_DEV_AGENT_NAME` constant (e.g. `"Davut Kember"`, matching the live-verified identity already documented in that file's own comment) or whether the UI should degrade to email-only when no name is available (D-13 doesn't explicitly cover the standalone-dev fallback case, only the plugin-mode `agent.fullName` vs. bootstrap-not-yet-complete case).
   - Recommendation: add `DEFAULT_DEV_AGENT_NAME = "Davut Kember"` alongside the existing `DEFAULT_DEV_AGENT_EMAIL`, mirroring the exact same live-verified-identity comment pattern already in that file.
