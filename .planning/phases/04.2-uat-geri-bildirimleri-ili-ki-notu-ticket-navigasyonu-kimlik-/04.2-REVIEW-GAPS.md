# Phase 04.2 (gap closure): Code Review Report

**Reviewed:** 2026-08-17T17:06:02Z
**Depth:** standard
**Diff base:** `b5a54fa..HEAD` (9 commits: `ec318b2`, `34a2000`, `9178182`, `4a08c39`, `b53a3e7`, `f46f7b9`, `442c0ca`, `21998d2`, `fe71a94`)

## Summary

The mechanical part of the gap closure is correct. `assertSideConversationLink` is hoisted ahead of both `isCurrent` gates, is `await`ed on all three return paths, error containment holds (the function has no reachable rejection path — every `await` sits inside a `try`/`catch`, and body construction is a pure template literal), the retry ceiling is a hard 2 (`HttpHandler.send` has no internal retry; `defaultOptions.mutations.retry` is `false` in both the prod and test QueryClient), and the retry is structurally comment-free so it cannot append a duplicate note. The D-01 ordering (`await linkAssertion` before `refreshCanonicalAfterMutation`) is preserved at `side-conversation-queries.ts:733`. The old "never calls addInternalNote when not current" contract is genuinely deleted, not shadowed — no surviving test asserts it. All 65 tests in the three suites pass (`craco test --watchAll=false`).

The problem is that the closure fixes *when* the write is attempted without fixing *which write actually persists the field*. Per `04.2-RESEARCH.md` §"Adjacent finding", the one and only live-proven mechanism for persisting `tu.side_conversation_parent` on a fresh ticket is a **`fields`-only `PATCH public/v1/tickets/{key}`**. The implementation puts that proven call on the *failure* branch and puts an **unprobed** `/v2` comment+fields PATCH on the success branch — on the same `/v2` host whose `fields` array was measured dropping this exact field 2/2 times. On the normal, everything-returns-200 path, the proven mechanism never runs. That is the same "side ticket becomes unfindable" failure class the phase set out to close (CR-01).

Secondary concerns: the load-bearing field write is gated behind an agent-identity check it does not need (WR-01), the first `console.error` mis-attributes a link loss that may not have happened (WR-02), and — most relevant to a hoist review — **no test locks the `await`**; the one ordering test became tautological the moment the call moved to the top of the function (WR-03). The new `environment-static.test.ts` gate blocks backticks but not the concatenation the file already performs, so it does not actually block the threat it names (WR-05/WR-06).

## Critical Issues

### CR-01: The success path never executes the only live-proven parent-field write; the proven write is reachable only on transport error

**File:** `src/query/side-conversation-queries.ts:663-685` (with `src/grispi/client/tickets.ts:116-126` / `165-181`)

**Issue:**
`assertSideConversationLink` returns immediately after a successful `addInternalNote`:

```ts
try {
  await grispiAPI.tickets.addInternalNote(sideKey, body); // /v2 PATCH, comment + fields
  return;                                                 // ← proven write never reached
} catch { ... }

try {
  await grispiAPI.tickets.patchTicketFields(sideKey, {    // public/v1, fields-only — THE proven write
    fields: [{ key: SIDE_CONVERSATION_PARENT_FIELD_KEY, value: parentKey }],
  });
} catch { ... }
```

The evidence base does not support this ordering:

- `04.2-RESEARCH.md:169` — two independent fresh creates via `POST /v2/tickets` with `fields` containing `tu.side_conversation_parent` read back **`null`** on both the create response and a direct `GET`, for 10+ minutes. `advanced-search` did not return them either.
- `04.2-RESEARCH.md:169` — "A **separate immediate `PATCH public/v1/tickets/{key}` with only `{"fields":[...]}`** persisted the value instantly and correctly."
- P1's probe body (`04.2-RESEARCH.md:106-116`) contains **only** `comment` — no `fields` key. `PATCH /v2/tickets/{key}` has therefore **never been probed for field persistence at all**. The only thing P1/P2/P3 proved about `/v2` PATCH is the `publicVisible:false` / no-email / status-untouched behaviour.

So the happy path is: `POST /v2` (field demonstrably dropped) → `PATCH /v2` with comment+fields (field persistence unverified, same host family that dropped it) → **200 → `return`**. The `public/v1` fields-only PATCH — the one write with live evidence behind it — only runs when attempt 1 throws at the transport level. A `/v2` PATCH that returns 200 while silently ignoring `fields` is indistinguishable from success here: no read-back, no log, no retry.

`fetchSideConversationPage` (`side-conversation-queries.ts:184-196`) filters the listing **exclusively** on `SIDE_CONVERSATION_PARENT_FIELD_KEY`. A side ticket that loses this field is created, emails the third party, and is then permanently invisible in the panel — the exact defect CR-01/verifier flagged, now merely relocated rather than closed.

**Fix:** make the proven write unconditional rather than a failure-branch fallback. Two options, in order of preference:

```ts
// Option A (recommended): always issue the proven fields-only write, then the
// note. The two are independent; the note never carries `fields` again.
await patchParentFieldWithLog(sideKey, parentKey);   // public/v1, fields-only — always
if (!agentEmail) { logNoIdentity(); return; }
await addNoteWithLog(sideKey, parentKey, agentEmail); // /v2, comment-only
```

```ts
// Option B (keeps D-23's 2-attempt shape): treat "note succeeded" as proof of
// nothing about `fields`, and still run the proven write.
try {
  await grispiAPI.tickets.addInternalNote(sideKey, body);
} catch {
  console.error("side-conversation-queries", "internal note PATCH failed — note lost", sideKey);
}
try {
  await grispiAPI.tickets.patchTicketFields(sideKey, {
    fields: [{ key: SIDE_CONVERSATION_PARENT_FIELD_KEY, value: parentKey }],
  });
} catch { /* separate console.error */ }
```

Either way this is a change to locked decision D-23's attempt sequencing and needs the decision re-opened, not a silent code edit. If D-23 must stand as written, the minimum acceptable mitigation is a live probe of `PATCH /v2/tickets/{key}` **with a `fields` array** against `gsocial-test`, recorded in RESEARCH.md, before this ships; and if that probe shows the field does not persist, D-23 is unimplementable as specified.

## Warnings

### WR-01: A missing agent email skips the load-bearing parent-field write, not just the note

**File:** `src/query/side-conversation-queries.ts:644-651`

**Issue:** The `!agentEmail` guard exists because the *note* needs a `creator`. It returns before the `fields` write, so an envelope without an agent identity produces a side ticket with neither the note nor the parent-field re-assertion — the same unfindability outcome as CR-01. The parent-field PATCH needs no identity at all. Currently unreachable in production only because `ComposeStore.submit` (`src/store/compose-store.ts:185-193`) bails on `!agentEmail`; the exported function itself carries no such protection, and `side-conversation-queries.test.tsx:1321` locks the current (wrong) behaviour in place.

**Fix:**
```ts
export async function assertSideConversationLink(sideKey, parentKey, agentEmail) {
  if (!agentEmail) {
    console.error("side-conversation-queries", "internal note skipped — no agent identity on envelope", sideKey);
    await patchParentField(sideKey, parentKey); // still load-bearing without an identity
    return;
  }
  ...
}
```
Update the test at `:1321` to assert `patchTicketFields` **was** called in that branch.

### WR-02: The first `console.error` claims the Grispi-side link may be missing before the retry that would restore it has run

**File:** `src/query/side-conversation-queries.ts:666-672`

**Issue:** Message 1 is `"internal note PATCH failed — side conversation may be missing its Grispi-side link"`. At that point the retry has not executed. When the retry succeeds, the link is *present* and only the note was lost, yet the operator sees a log asserting the opposite. D-23 requires the two losses to stay on separate, non-mixed lines; this one mixes the link concern into the note's message. The locking test (`side-conversation-queries.test.tsx:1266-1280`) asserts `toHaveBeenCalledTimes(1)` and never inspects the string, so the misattribution is unguarded.

**Fix:**
```ts
console.error(
  "side-conversation-queries",
  "internal note PATCH failed — the relationship note is lost for this side ticket (no retry, D-23)",
  sideKey
);
```
and add a content assertion, e.g. `expect(consoleErrorSpy.mock.calls[0][1]).not.toMatch(/link|listing/i)`.

### WR-03: No test locks the `await` on any return path; the D-01 ordering test became tautological after the hoist

**File:** `src/query/__tests__/side-conversation-queries.test.tsx:1235-1247`, `:1330-1355`

**Issue:** The core claim of the hoist — "Every return path awaits it (never a dangling promise)" (`side-conversation-queries.ts:706-708`) — is untested.

- `:1235` compares `mockedAddInternalNote.mock.invocationCallOrder[0] < invalidate.mock.invocationCallOrder[0]`. `invocationCallOrder` records **call** order, and the hoist makes `addInternalNote` fire unconditionally before every gate. Deleting `await linkAssertion` at `side-conversation-queries.ts:733` (turning the D-01 sequencing into fire-and-forget) leaves this assertion passing. Before the hoist it was a genuine ordering gate; it no longer is.
- `:1330` asserts `addInternalNote` was *called* on the abandoned-session path. Removing the `await linkAssertion` at `:719`/`:726` also leaves this passing, because the call already happened synchronously.

Net: every `await` added by `34a2000` can be deleted without a single test failing. (The tests *are* non-tautological for the hoist itself — reverting the hoist correctly fails `:1330` — and for D-23's retry target; the gap is specifically the awaits.)

**Fix:** assert completion, not invocation, using a deferred:
```ts
it("does not resolve executeCreateMutation until the link write has settled (all return paths)", async () => {
  const link = deferred<unknown>();
  mockedAddInternalNote.mockReturnValue(link.promise);
  const envelope = createEnvelope();
  let settled = false;
  const mutation = executeCreateMutation(client, boundary(), envelope).then(() => { settled = true; });
  selected = { ticketKey: "SIDE-B", parentKey: "PARENT-B", sessionKey: 2 }; // abandon
  for (let i = 0; i < 10; i += 1) await Promise.resolve();
  expect(settled).toBe(false);           // fails today if the await is removed
  link.resolve({ key: "SIDE-9" });
  await mutation;
  expect(settled).toBe(true);
});
```
Add the mirror case for the still-current path asserting the link promise settles before `invalidateQueries` *resolves* (not merely before it is called).

### WR-04: `patchTicketFields`'s `ts.status` guard is exact-match and case-sensitive, and reports a programmer error as a transport failure

**File:** `src/grispi/client/tickets.ts:166-170`

**Issue:** The guard is correctly placed before `this.http.send` (verified: `tickets.test.ts:463` proves `send` is never reached), and `.some()` correctly scans every element of a multi-field body. But the comparison is `field.key === "ts.status"` verbatim, so `"TS.status"`, `"Ts.Status"`, or `" ts.status"` all pass through to `public/v1` and would re-open the D-15 hole this guard exists to close — the codebase has no evidence that Grispi field keys are case- or whitespace-sensitive on the write path. Separately, the guard throws a bare `Error`, and its only caller wraps the call in `catch { console.error("… re-assertion failed after retry — listing may not find this ticket") }` (`side-conversation-queries.ts:678-684`), so a future misuse would be logged as a network problem rather than as the contract violation it is.

**Fix:**
```ts
const LIFECYCLE_FIELD_KEY = "ts.status";
if (body.fields.some((f) => f.key?.trim().toLowerCase() === LIFECYCLE_FIELD_KEY)) {
  throw new TicketFieldWriteError(
    "patchTicketFields must not write ts.status — use Tickets.patchTicket for lifecycle transitions (D-15)"
  );
}
```
and add negative test cases for `"TS.STATUS"` and `" ts.status"` alongside `tickets.test.ts:463`.

### WR-05: The `environment.ts` static gate does not block the threat it names — the file already concatenates a host from a variable

**File:** `src/grispi/client/__tests__/environment-static.test.ts:4-15, 40-42`

**Issue:** The header states the gate exists because "a template literal injected into its code would let a host string be silently interpolated." But `buildAgentTicketUrl` (`environment.ts:69-76`) *already* interpolates a host by string concatenation:

```ts
return "https://" + tenantId + ".grispi." + grispiTld(env) + "/tickets/" + encodeURIComponent(ticketKey);
```

Any future accidental host interpolation written with `+` — including one derived from an untrusted value — passes this gate unchanged. The test therefore provides assurance that the stated threat model does not actually earn, which is worse than no gate for a security control (a reviewer who sees "static gate: PASS" stops looking).

**Fix:** either re-scope the test's doc-comment to what it truly enforces ("no template literals, a *style* constraint that keeps the file grep-auditable — it is not a host-injection control"), or make it enforce the real invariant, e.g. assert that no identifier is concatenated into a string that begins with `https://` outside `GRISPI_BASE_URLS`, or move `buildAgentTicketUrl` out of the gated file and assert the gated file contains no string concatenation at all.

### WR-06: The comment stripper can silently vacuum live code, and the "URL values survived" test never checks a URL value

**File:** `src/grispi/client/__tests__/environment-static.test.ts:23-34, 48-54`

**Issue:** Two distinct weaknesses in the gate's anti-vacuity story:

1. `source.replace(/\/\*[\s\S]*?\*\//g, "")` is a naive block-comment strip with no string/regex-literal awareness. A future `"…/*…"` inside any string or regex literal in `environment.ts` opens a comment region that swallows everything up to the next `*/` — most likely the end of a later doc-comment — deleting the intervening real code. The four anti-vacuity assertions (`GRISPI_BASE_URLS`, `preprod`, `prod_tr`, `/\bprod:/`) all sit in lines 6-10, so any vacuuming that starts after line 10 is undetectable.
2. The test named `"still contains the three environment keys after stripping (line-comment strip did not eat the // in https:// URL values)"` asserts only the three **keys**. It never asserts that a single `https://` survived. The parenthetical claims a guarantee the assertions do not make; if the values were ever emitted on their own lines and the line-strip regex were loosened, the test would keep passing.

**Fix:**
```ts
it("keeps every host value intact after stripping", () => {
  for (const url of Object.values(GRISPI_BASE_URLS)) {
    expect(strippedSource).toContain(url);   // asserts the https:// values, not just the keys
  }
  expect(strippedSource.split("https://")).toHaveLength(4); // exactly 3 host literals remain
});
```
and bound the vacuum risk by asserting a floor on retained size, e.g. `expect(strippedSource.trim().split("\n").length).toBeGreaterThan(20)`.

### WR-07: `InternalNotePatchRequest`'s doc-comment presents an unverified mechanism as "proven"

**File:** `src/types/grispi.type.ts:322-329`

**Issue:**
> "A live probe showed `POST /v2/tickets`'s `fields` array can fail to persist this field on a freshly created ticket, but a follow-up `fields`-only PATCH persists it immediately — **this type carries that proven mechanism** as a near-zero-cost addition to a PATCH already being sent."

The probe proved a `fields`-**only** `PATCH public/v1/tickets/{key}` (`04.2-RESEARCH.md:169`). `InternalNotePatchRequest` is neither `fields`-only nor on `public/v1` — it is a comment+fields `/v2` PATCH, a shape that was never probed. The comment claims inherited evidence the shape does not have, and it is the reasoning that made CR-01 look safe. The same over-claim is repeated at `src/grispi/client/tickets.ts:103-114` ("re-asserts its `tu.side_conversation_parent` field (D-22)") without any caveat.

**Fix:** amend both doc-comments to state plainly that `/v2` PATCH `fields` persistence is **unverified**, and that the proven mechanism is `TicketFieldsPatchRequest` on `public/v1`. Resolve alongside CR-01.

## Info

### IN-01: "Every return path awaits it" is true for `return`s but not for a synchronous throw

**File:** `src/query/side-conversation-queries.ts:706-708, 712-727`

**Issue:** If `boundary.activeConversation.bindCreatedTicket`, `boundary.bindCreatedTicket`, or `mutationAccepted` (lines 722-728) threw synchronously, `executeCreateMutation` would reject with `linkAssertion` never awaited. This is currently harmless in practice — `assertSideConversationLink` cannot reject (every `await` is inside a `try`/`catch` and body construction is a pure template literal), so no unhandled rejection is possible, and all three store methods self-guard with `isCurrent`/`isRetained` and cannot throw (`src/store/active-conversation-store.ts:420-458`). Worth narrowing the comment's absolute claim so a future edit that makes any of those three throwable does not silently invalidate it.

**Fix:** reword to "every `return` path awaits it; the block between creation and the first `await` is deliberately throw-free (three self-guarding MobX actions)".
