# Phase 04.2 Plan 01: Internal-note write path + detail recipient fallback Summary

**New side tickets get a silent `publicVisible:false` internal note plus a re-asserted `tu.side_conversation_parent` field via one `/v2/tickets` PATCH awaited before the detail refetch, and the detail screen resolves the recipient through `users.getUser` even before a third party has replied.**

## Accomplishments
- `InternalNotePatchRequest` type + `Tickets.addInternalNote` client method — sibling of `ReplyTicketPatchRequest`/`replyTicket`, `publicVisible` narrowed to the `false` literal, targets `PATCH v2/tickets/{key}`
- `formatInternalNoteBody(parentKey)` — pure, D-02-locked plain-text body with the parent ticket key as the sole interpolation point
- `assertSideConversationLink` wired into `executeCreateMutation`, awaited between `mutationAccepted` and `refreshCanonicalAfterMutation`'s detail refetch (RESEARCH.md Pitfall #1): fires the internal note + D-22 parent-field re-assertion, retries once on failure, never throws, logs two separate `console.error` lines on final failure
- `resolveDetailRecipientFallback` — detail-path port of the existing list-path `hydrateSummaries` fallback; resolves the recipient via `grispiAPI.users.getUser` when no `ROLE_END_USER` comment exists yet, wired into `sideConversationDetailOptions().queryFn`

## Decisions Made
- `assertSideConversationLink` is called unwrapped (no surrounding `try/catch`) at its call site since the function itself is guaranteed never to throw — keeps D-04's "never fails the caller" contract in exactly one place

- `resolveDetailRecipientFallback` reuses `hydrateSummaries`'s exact fallback shape rather than inventing a new resolution path, per D-12's explicit scope limit
