## Summary

Phase 04.2 delivers nine UAT fixes across the write path (silent internal note +
`tu.side_conversation_parent` re-assertion), agent-UI deep links, identity
rendering, the info box, the composer toolbar collapse and the parent banner.
Phase invariants that I actively verified and found **intact**:

- `tu.side_conversation_parent` is never read from settings; only the hardcoded
  constant and one duplicated literal exist (see WR-06).
- No Grispi host literal exists outside `GRISPI_BASE_URLS`
  (`grep` over all of `src/`, excluding tests, returns nothing).
- `environment.ts` contains no template literals in code (backticks appear only
  inside doc-comment prose) — but nothing enforces this (WR-03).
- Every external `<a>` added this phase carries `target="_blank"` **and**
  `rel="noopener noreferrer"` (`ticket-key-link.tsx`, `parent-banner.tsx`,
  `thread-message.tsx`).
- The iframe hash `origin` parameter is never read anywhere in the reviewed set.
- The token is written to `Authentication.headers` only and never persisted.
- `InternalNotePatchRequest.comment.publicVisible` is narrowed to the `false`
  literal and `assertSideConversationLink` sends it literally — the internal note
  cannot become requester-visible through this code path.

Two findings are blocking. The first is a real data-integrity hole in the create
mutation: the D-22 parent-field re-assertion — which the phase's own research
says is required because `POST /v2/tickets`'s `fields` array can silently fail to
persist — is gated behind the same `isCurrent` check as the cosmetic internal
note, so a mid-create conversation switch leaves a side ticket permanently
orphaned from its parent. The current test suite *locks this behaviour in*
(`side-conversation-queries.test.tsx:1294`), so it will not be caught later.
The second is the hardcoded dev identity: I traced a concrete path where
`DEFAULT_DEV_AGENT_EMAIL` is sent to the live API as the `us.email` comment
creator and rendered as a sender name, even while the plugin is running inside
the real Grispi iframe.

## Critical Issues

### CR-01: A mid-create conversation switch permanently orphans the created side ticket (D-22 re-assertion skipped)

**File:** `src/query/side-conversation-queries.ts:700-716`
**Issue:**
`executeCreateMutation` returns early when the agent's selection has moved on:

```ts
if (!isCurrent(boundary, envelope)) return;            // 700 — ticket ALREADY created
boundary.activeConversation.bindCreatedTicket(envelope, sideKey);
boundary.bindCreatedTicket(envelope.sessionKey, sideKey);
if (!isCurrent(boundary, envelope, sideKey)) return;   // 703 — ticket ALREADY created
boundary.activeConversation.mutationAccepted(envelope);
await assertSideConversationLink(...);                 // 712 — never reached
```

`assertSideConversationLink` is the **only** place in the codebase that PATCHes
`tu.side_conversation_parent` onto the created side ticket (verified by grep —
the sole other write of that key is `compose-store.ts:215`, inside the `POST`
body). `types/grispi.type.ts:322-329` records the live finding that motivated
D-22: *"a live probe showed `POST /v2/tickets`'s `fields` array can fail to
persist this field on a freshly created ticket, but a follow-up `fields`-only
PATCH persists it immediately."*

Consequence: if `POST` drops the field **and** the PATCH is skipped, the side
ticket exists in the tenant, has emailed the third party, and can never be found
again — `fetchSideConversationPage` searches exclusively by
`allConditions: [{ fieldKey: SIDE_CONVERSATION_PARENT_FIELD_KEY, ... }]`
(line 186-194). There is no reconciliation path.

Reachability is ordinary, not exotic. `bindCreatedTicket`
(`panel-navigation-store.ts:107-118`) no-ops once
`selectedConversation.sessionKey` has advanced, and both `openConversation`
(clicking another row) and `reservePendingConversation` (starting a second
compose) increment `selectedConversationSession`. Any of those during a
multi-second create POST trips the gate.

The doc-comment on `assertSideConversationLink` (line 625-634) itself states the
two concerns have different weight — *"the parent field is load-bearing for
listing while the note itself is not"* — yet both were placed behind one gate.

**Fix:** Hoist the parent-field assertion out of the session gate. It depends on
nothing but `sideKey` and `envelope.parentKey`, both known at line 694.

```ts
// after: sideKey = response.key;
// Unconditional — D-22's field re-assertion is a property of the TICKET,
// not of the agent's current selection. Never gated on isCurrent.
const linkPromise = assertSideConversationLink(
  sideKey,
  envelope.parentKey,
  envelope.request.comment.creator[0]?.value ?? null
);

if (!isCurrent(boundary, envelope)) {
  await linkPromise;   // still swallows internally (D-04)
  return;
}
boundary.activeConversation.bindCreatedTicket(envelope, sideKey);
boundary.bindCreatedTicket(envelope.sessionKey, sideKey);
await linkPromise;     // Pitfall #1 ordering preserved
if (!isCurrent(boundary, envelope, sideKey)) return;
boundary.activeConversation.mutationAccepted(envelope);
...
```

Then update `side-conversation-queries.test.tsx:1294` — the test named *"never
calls addInternalNote when the agent has switched to a different conversation"*
currently asserts the defect. It should instead assert the PATCH **is** sent with
the parent field while the UI-side reconcile steps are skipped.

### CR-02: Hardcoded developer identity is sent to the live API as the comment `creator` and rendered as a sender name, including while running inside the real Grispi iframe

**File:** `src/lib/standalone-dev.ts:39,45,79-82`
**Issue:**
`DEFAULT_DEV_AGENT_EMAIL = "davutkmbr@gmail.com"` / `DEFAULT_DEV_AGENT_NAME =
"Davut Kember"` are not inert dev conveniences — they are load-bearing inputs to
the write path. Traced end to end:

1. `standalone-dev.ts:79-82` — `agentEmail`/`agentName` fall back to the
   hardcoded constants whenever `REACT_APP_DEV_AGENT_EMAIL`/`_NAME` are unset.
2. `grispi-context.tsx:87` — `const plugin = standaloneConfig ? null :
   getPluginInstance();`. The SDK bridge is disabled **whenever
   `standaloneConfig` is non-null**, not whenever the bridge is absent. The
   activation rule is `NODE_ENV === "development" && REACT_APP_DEV_TOKEN` — both
   of which hold when the CRA dev server (`localhost:3000`) is loaded *inside the
   real Grispi panel iframe*, which is exactly how this project's live UAT is
   run. In that configuration the genuine `bundle.context.agent.email` is
   discarded and never read.
3. `grispi-context.tsx:193-194` — `setAgentEmail(standaloneConfig.agentEmail)`.
4. `compose-screen.tsx:29,72-82` → `compose-store.ts:203` —
   `creator: [{ key: "us.email", value: agentEmail }]` inside
   `CreateTicketRequest`. The hardcoded address becomes the **author of a real
   outbound email** on a real tenant.
5. `side-conversation-queries.ts:715` — the same value is forwarded into
   `assertSideConversationLink`, so the internal note is authored by it too.
6. `thread-message.tsx:52-68` — `agentName` is the `pendingOwnFallback` sender
   label, and `isCurrentAgent` (the "Siz" badge) is
   `message.senderEmail === agentEmail`. Another developer's own messages
   therefore render *without* the "Siz" badge while Davut's render *with* it.

The severity driver is not the constant's presence, it is that the fallback is
**silent and load-bearing**. `compose-screen.tsx:45-52` already disables send
when `!agentEmail`; removing the fallback converts this from "sends as the wrong
person" into a visible, correct "cannot send". The fallback deliberately trades a
loud failure for silent misattribution.

Production builds cannot activate this (`NODE_ENV !== "development"` short-circuits
at `standalone-dev.ts:66`), so this is not a shipped-artifact vulnerability — it is
a write-path correctness defect that fires on every non-Davut local/UAT session
against a shared tenant.

**Fix:** Delete both constants and make the identity required-or-disabled.

```ts
// standalone-dev.ts — no identity fallback at all
const agentEmail = env.REACT_APP_DEV_AGENT_EMAIL?.trim() || null;
const agentName  = env.REACT_APP_DEV_AGENT_NAME?.trim()  || null;
// StandaloneDevConfig: agentEmail: string | null; agentName: string | null;
```

`compose-screen`'s and `chat-screen`'s existing `!agentEmail` guards then disable
send with no further change. If a source is wanted rather than an env var, the
`sub`/`email` claim on the dev token is already parseable —
`lib/grispi-environment.ts:22` (`parseJwt`) exists and is exported; resolve the
identity from the token the dev already supplies instead of from a literal.

## Warnings

### WR-01: `buildAgentTicketUrl` interpolates `tenantId` into the host with no encoding or validation

**File:** `src/grispi/client/environment.ts:64-77`
**Issue:** `ticketKey` is passed through `encodeURIComponent`; `tenantId` is not.
A `tenantId` containing `/`, `@`, `?` or `#` re-points the resulting
`target="_blank"` link at a different origin — e.g. `tenantId = "evil.com/x"`
yields `https://evil.com/x.grispi.net/tickets/K`, whose host is `evil.com`. The
doc-comment argues all inputs are trusted (`bundle.context.tenantId`), which is
true today, but this function is the single URL-construction choke point for the
whole phase and defends only one of its two interpolated inputs.

**Fix:**
```ts
export function buildAgentTicketUrl(
  tenantId: string,
  env: GrispiEnvironment,
  ticketKey: string
): string {
  if (!/^[a-z0-9][a-z0-9-]*$/i.test(tenantId)) {
    throw new Error("buildAgentTicketUrl: unsafe tenantId");
  }
  return "https://" + tenantId + ".grispi." + grispiTld(env) + "/tickets/" +
    encodeURIComponent(ticketKey);
}
```
(A thrown error is preferable to a silently wrong link; `ParentBanner` already
has a no-href branch, and `chat-screen.tsx:323` already guards on `tenantId`.)

### WR-02: `grispiTld` fails open when a base URL stops matching its prefix regex

**File:** `src/grispi/client/environment.ts:49-51`
**Issue:** `GRISPI_BASE_URLS[env].replace(/^https:\/\/api\.grispi\./, "")`
returns the **entire unmodified URL** when the pattern does not match. Adding a
future entry such as `eu: "https://eu-api.grispi.com"` silently produces
`https://tenant.grispi.https://eu-api.grispi.com/tickets/K`. The failure is
invisible until a user clicks the link.
**Fix:**
```ts
export function grispiTld(env: GrispiEnvironment): string {
  const match = /^https:\/\/api\.grispi\.(.+)$/.exec(GRISPI_BASE_URLS[env]);
  if (!match) throw new Error("grispiTld: unmapped base URL for " + env);
  return match[1];
}
```

### WR-04: `bootstrapPluginInit` opens the CORE-04 gate before writing the auth headers, contradicting its own documented contract

**File:** `src/contexts/plugin-bootstrap.ts:98-107`
**Issue:** The `onEnvironmentReady` doc-comment (line 66-79) states the gate
"becomes true only once every request the plugin can issue is bound to the
resolved host **AND** the resolved tenant credentials." The code does the
opposite ordering:
```ts
deps.setEnvironment(resolvedEnvironment);
deps.setEnvironmentState(resolvedEnvironment);
deps.onEnvironmentReady();                      // gate opens
deps.authentication.setTenantId(bundle.context.tenantId);   // credentials AFTER
deps.authentication.setToken(bundle.context.token);
```
No exploitable window exists **today** — the block is synchronous and
`bundle.context.token` is already dereferenced at line 96, so a malformed bundle
throws before the gate opens. But the whole point of the WR-01/CORE-04 mitigation
is that a future `await` or an early-return inserted between these lines re-opens
the header-leak race, and the comment actively misleads the next editor into
thinking that is already impossible.
**Fix:** Move `deps.onEnvironmentReady()` to immediately after
`deps.authentication.setToken(...)`, matching the stated contract, and drop the
now-inaccurate clause from the comment.

### WR-05: `assertSideConversationLink`'s retry has no idempotency guard — a transport failure after a committed PATCH duplicates the internal note

**File:** `src/query/side-conversation-queries.ts:659-680`
**Issue:** The retry replays the byte-identical `InternalNotePatchRequest` after
*any* failure, including a network timeout or aborted response where the server
already applied the PATCH. `PATCH /v2/tickets/{key}` with a `comment` **appends**
a comment (that is precisely why `patchTicket` was kept on `public/v1` for
status-only writes — `tickets.ts:127-139`), so the agent sees two identical
"Bu talep, X talebinin yan konuşmasıdır" notes in the thread. The first `catch`
is also blind to permanent failures — a 422/403 is retried for nothing.
**Fix:** Retry only on `NetworkError` and only for the `fields`-only half:
```ts
try {
  await grispiAPI.tickets.addInternalNote(sideKey, body);
  return;
} catch (error) {
  if (!(error instanceof NetworkError)) { /* log + return */ }
}
// Retry WITHOUT the comment — re-asserting `fields` is idempotent,
// appending a comment is not.
try {
  await grispiAPI.tickets.patchTicketFields(sideKey, {
    fields: [{ key: SIDE_CONVERSATION_PARENT_FIELD_KEY, value: parentKey }],
  });
} catch { /* existing two console.error lines */ }
```
(If a `fields`-only PATCH on `/v2/tickets` 500s per probe finding N2, route the
retry through `patchTicket`'s `public/v1` host instead — the field write is not
`ts.status`, so D-15 is untouched.)

### WR-06: The D-01/D-02 parent-field key has two sources of truth

### WR-07: The blocked "Yeni konuşma" reason is unreachable — it lives only on a disabled control

**File:** `src/screens/conversations-list-screen.tsx:67-84`
**Issue:**
```tsx
aria-label={isSideConversation ? NEW_CONVERSATION_BLOCKED_LABEL : NEW_CONVERSATION_LABEL}
title={isSideConversation ? NEW_CONVERSATION_BLOCKED_LABEL : undefined}
disabled={isSideConversation}
```
`title` is set **only in the disabled state**. Browsers do not dispatch mouse
events to disabled form controls, so the native tooltip never renders; the
element is also removed from the tab order, so the `aria-label` is never
announced. The blocked explanation reaches no user through this control at all.
The `ParentBanner` carries the message in the list body, which is why this is a
warning and not a blocker — but the two disabled-state affordances added here are
dead weight.
**Fix:** Keep the button focusable and explain the state, rather than disabling it:
```tsx
aria-disabled={isSideConversation}
title={NEW_CONVERSATION_BLOCKED_LABEL}   // always present, tooltip works
onClick={() => { if (!isSideConversation) panelNavigation.openCompose(); }}
className={cn("gap-1 px-2 text-primary", isSideConversation && "opacity-50")}
```
(`aria-disabled` keeps the control in the tab order so screen-reader and
keyboard users receive the reason; the click guard preserves D-11's block.)

### WR-08: `InfoBox` dismiss button is 24×24px, below the project's own interactive floor

### WR-09: Remote `attachment.objectUrl` reaches `href`/`src` with no protocol allowlist

**File:** `src/screens/components/thread-message.tsx:120-152`
**Issue:** `<a href={attachment.objectUrl}>` and `<img src={attachment.objectUrl}>`
consume an API-supplied string directly. Every other URL sink in this codebase is
gated: `html-sanitizer.ts:50` enforces
`ALLOWED_URI_REGEXP: /^(?:https?:\/\/|mailto:)/i`, and
`rich-text-composer.tsx:224-241` runs `isAllowedLink` before `setLink`. The
attachment path is the sole exception, and its content originates from a third
party's inbound email. A `javascript:`/`data:text/html` value here is a
click-to-XSS in the agent's panel.
**Fix:** Reuse the existing predicate rather than adding a fourth policy:
```ts
const safeUrl = (url: string | undefined) =>
  url && /^https:\/\//i.test(url) ? url : undefined;
// then href={safeUrl(attachment.objectUrl)} / src={safeUrl(...)}
```
Skip rendering (or render a non-link chip) when it returns `undefined` —
`grispi.type.ts:36-38` already documents `objectUrl` as always `https://`, so a
non-matching value is by definition anomalous.

### WR-10: `resolveDetailRecipientFallback` treats a null/empty requester field as user id `0`

**File:** `src/query/side-conversation-queries.ts:543-547`
**Issue:**
```ts
const requesterId = Number(ticket.fieldMap?.["ts.requester"]?.value);
if (!Number.isFinite(requesterId)) return detail;
```
`Number(null)` and `Number("")` are both `0`, which is finite — so a ticket whose
`ts.requester` entry exists but carries a null/empty value issues
`grispiAPI.users.getUser(0)` on every detail load. `Number(undefined)` → `NaN`
is caught, so only the missing-key case is actually guarded. `FieldMap.value` is
typed `any` (`grispi.type.ts:110`), so neither shape is excluded by the type
system.
**Fix:**
```ts
const raw = ticket.fieldMap?.["ts.requester"]?.value;
const requesterId = typeof raw === "number" ? raw : Number(String(raw ?? "").trim());
if (!Number.isInteger(requesterId) || requesterId <= 0) return detail;
```
The same coercion at `resolveRecipientLabel` (line 457) is benign — `NaN`/`0`
simply never matches a `creator.id` — but is worth aligning for consistency.

### IN-04: `parentKeyOfTicket` re-reads the field map behind a cast

**File:** `src/lib/side-conversation.ts:107-112`

**Fix:** Read once and share:
```ts
export function parentKeyOfTicket(ticket: Ticket | null): string | null {
  if (!isHydratedTicket(ticket)) return null;
  const value = ticket.fieldMap[SIDE_CONVERSATION_PARENT_FIELD_KEY]?.value;
  if (typeof value !== "string") return null;
  const trimmed = value.trim();
  return trimmed === "" ? null : trimmed;
}
// then: isSideConversationTicket = (t) => parentKeyOfTicket(t) !== null;
```
