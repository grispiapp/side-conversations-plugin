# Phase 04.2 Plan 05: Composer toolbar popover + compact-viewport token set Summary

**Split the 10-button composer toolbar into a 4-control direct row plus a single accessible "Aa" popover holding the 7 formatting actions, and added a `@media (max-height: 620px)` CSS token set shrinking panel chrome on short viewports.**

## Performance

- **Duration:** ~40 min
- **Completed:** 2026-08-17T15:04:04Z
- **Tasks:** 2
- **Files modified:** 5 (2 source components, 1 CSS file, 2 test files)

## Accomplishments

- `DIRECT_ACTIONS` (attach/undo/redo) and `FORMAT_ACTIONS` (bold/italic/heading/link/bulletList/orderedList/blockquote) replace the flat `TOOLBAR_ACTIONS` array; toolbar now renders exactly 4 direct controls
- New `FormatMenu` popover: opens `bottom-full` (upward), `role="menu"` with 7 `role="menuitemcheckbox"` items, full keyboard contract (Arrow up/down wrap, Home/End, Escape returns focus, Tab closes without forcing focus, outside mousedown closes) — lifecycle copied verbatim from `chat-screen.tsx`'s proven conversation-options menu
- `heading`/`link` items close the popover and hand off to their existing docked sub-panels unchanged (`headingMenuOpen`/`linkEditorOpen`, zero rewrite); `runToolbarAction` execution logic is completely untouched, only its trigger locations moved
- Removed the toolbar row's `overflow-x-auto` helper class — the horizontal-scroll defect UX-07 targets
- New `@media (max-height: 620px)` block in `index.css`, written outside any `@layer` so it outranks the Tailwind utility classes it overrides: `--panel-header-height` 3rem→2.5rem, `--panel-inset` 1rem→0.75rem, `.side-conversation-row` min-height 72px→56px, reply editor min/max 96/160px→64/112px, compose editor min-height 192px→128px
- `--interactive-target` and every `font-size`/typography rule left untouched (accessibility floor / D-21 — the "everything looks zoomed" report was a local dev artefact, not a product bug)

## Decisions Made

- `closeLinkEditor`/`closeHeadingMenu` now focus `formatTriggerRef` (the "Aa" button) instead of the old `linkTriggerRef`/`headingTriggerRef`, since the link/heading buttons only exist while the popover is open — by the time either sub-panel closes, the popover (and thus its DOM node) is already gone
- FormatMenu's `onBlur` close-guard exempts focus moving into the composer's own editor DOM node (`editorRef.current?.view.dom.contains(nextFocus)`), not just into the panel itself — required because `runToolbarAction`'s bold/italic/list/quote branches call `editor.chain().focus()...run()`, which is an intentional focus transfer that must not close the still-toggling panel
- Compact CSS rules are written outside any `@layer` (not `@layer components`) specifically so they win the specificity fight against the Tailwind utility classes they override — matches the file's existing pattern of `@layer base` blocks only for token/reset definitions

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] FormatMenu onBlur would close the panel on every bold/italic/list/quote toggle**
- **Found during:** Task 1 (writing the FormatMenu popover tests)
- **Issue:** The plan's UI-SPEC JSX includes an `onBlur` handler on the panel copied from `chat-screen.tsx`'s menu (checks `relatedTarget` against the panel only). Since `runToolbarAction`'s bold/italic/bulletList/orderedList/blockquote branches call `editor.chain().focus()...run()`, clicking any of those items moves DOM focus into the editor mid-click, which the naive onBlur guard reads as "focus left the panel" and closes it — directly violating the required "toggle keeps the panel open" behavior (a `must_haves.truths` line item).
- **Fix:** Extended the onBlur guard to also treat focus moving into this composer's own editor DOM node as staying "inside" the interaction, alongside the existing panel-containment check.
- **Files modified:** src/screens/components/rich-text-composer.tsx
- **Verification:** New test asserts the panel stays open (`formatMenuPanel()` non-null) after clicking Kalın; full suite green.
- **Committed in:** 0cc46a6 (Task 1 commit)

**2. [Rule 1 - Bug] Focus-return refs pointed at unmountable popover items**
- **Found during:** Task 1 (implementing the "existing focus-return behavior preserved" instruction)
- **Issue:** The plan's literal instruction ("link ve heading artık toolbar'da olmadığı için o iki ref popover öğelerine taşınır") would have `linkTriggerRef`/`headingTriggerRef` point at the popover's Bağlantı/Başlık buttons. But clicking either of those items immediately closes the popover (`closeFormatMenu(false)`), unmounting that DOM node — by the time `closeLinkEditor`/`closeHeadingMenu` run (on Uygula/İptal/Escape/Bağlantıyı kaldır), the ref would already be null, silently stranding focus at `<body>` instead of returning it anywhere.
- **Fix:** Repointed both focus-return calls at `formatTriggerRef` (the always-mounted "Aa" button) instead, removing the now-unused `linkTriggerRef`/`headingTriggerRef` ref objects entirely.
- **Files modified:** src/screens/components/rich-text-composer.tsx
- **Verification:** "creates safe links..." test now asserts focus lands on the Aa trigger after applying/removing a link.
- **Committed in:** 0cc46a6 (Task 1 commit)

**3. [Rule 1 - Bug, out-of-plan file] thread-components.test.tsx regression**
- **Found during:** Task 2 (running the `CI=true npm test` full-suite gate)
- **Issue:** `thread-components.test.tsx` (not in Task 1's `<files>` list, so not updated in Task 1) also renders `RichTextComposer` directly and asserted on the seven formatting buttons by `aria-label` without opening the FormatMenu popover — 2 tests failed after Task 1's toolbar split.
- **Fix:** Updated both affected tests to open the "Aa" popover (`button("Biçimlendirme seçenekleri").click()`) before looking up formatting-action buttons, matching the pattern already used in `rich-text-composer.test.tsx`.
- **Files modified:** src/screens/components/__tests__/thread-components.test.tsx
- **Verification:** Full `CI=true npm test -- --watchAll=false` → 479/479 passing.
- **Committed in:** 6008ddb (Task 2 commit)

**4. [Grep-gate wording] Doc comments accidentally matched literal acceptance-criteria greps**
- **Found during:** Task 2 (self-verifying acceptance criteria)
- **Issue:** Explanatory comments in `index.css` and `conversation-row.tsx` used the literal tokens `interactive-target`, `font-size`, `side-conversation-row`, and `min-h-[72px]` in prose, inflating grep counts the plan's acceptance criteria pin to exact values (1/0/2/2 respectively).
- **Fix:** Reworded the comments to describe the same intent without the exact literal substrings (e.g. "interactive hit-area floor token" instead of the literal CSS variable name in prose).
- **Files modified:** src/index.css, src/screens/components/conversation-row.tsx
- **Verification:** All plan-specified grep counts re-checked and match exactly.
- **Committed in:** 6008ddb (Task 2 commit)
