<objective>
Close code-review finding **WR-01** (04.1-REVIEW.md), which is the single blocking
gap in `04.1-VERIFICATION.md` (`status: gaps_found`).

`src/contexts/grispi-context.tsx:184-199` invokes `bootstrapPluginInit({...})`
fire-and-forget, so it returns at its first `await` (`plugin._init()`). The very
next synchronous statement registers `plugin.currentTicketUpdated`, whose handler
calls `switchTicket` -> `grispiAPI.tickets.getTicket` -> `HttpHandler.send` on the
shared `httpHandler`. If the Grispi SDK emits a ticket-update event before the
bootstrap promise resolves, that fetch runs while `HttpHandler.baseUrl` is still
the class-field default — which phase 04.1 changed from preprod (`api.grispi.net`)
to prod (`api.grispi.com`). A preprod tenant's early ticket-switch request
therefore hits **PRODUCTION**: the exact failure mode CORE-04 exists to prevent.
The same window also carries empty auth headers (no `tenantId`, no
`Authorization`).

Purpose: restore the phase's stated invariant — "no request in plugin mode ever
goes to the wrong host" — and give it its first behavioral test. `grispi-context.tsx`
is currently rendered by **zero** tests (all four consuming test files mock
`@/contexts/grispi-context` wholesale), so the race is completely unproven either way.

Output: a gated ticket-update handler, a `onEnvironmentReady` bootstrap dep that
owns the ordering invariant, and a new `src/contexts/__tests__/grispi-context.test.tsx`
that renders the real provider and fails on the pre-fix code.
</objective>

<design_decisions>

These are the judgment calls the fix hinges on. Executor: implement these as
decided; do not re-litigate.

**DD-1 — Where the ref flips: a new injected `onEnvironmentReady()` dep called
from inside `bootstrapPluginInit`'s success path, immediately after
`deps.setEnvironment(...)`.**

04.1-REVIEW.md sketched two variants. `.finally()` on the caller side is WRONG:
`finally` also runs on the reject path, where `_init()` never produced a bundle,
`setEnvironment` was never called, and `baseUrl` is still the class default —
opening the gate there re-creates the exact bug on the failure path.
`04.1-VERIFICATION.md`'s `missing` list names the success-path variant for this
reason.

It cannot be flipped by the caller after the promise resolves either, because
`bootstrapPluginInit` itself calls `deps.switchTicket(bundle.context.ticketKey)`
at `plugin-bootstrap.ts:74` — the gate must already be open by then. So the flip
belongs INSIDE `bootstrapPluginInit`, keeping `plugin-bootstrap.ts` the single
place that knows the ordering invariant (it already owns the "no `await` between
setEnvironment and switchTicket" comment at lines 60-63).

Placed immediately after `deps.setEnvironment(...)` per the VERIFICATION wording.
Note this is functionally identical to placing it after the auth writes: lines
64-74 are one uninterrupted synchronous block with no `await`, so no SDK event
can interleave between `setEnvironment` and `authentication.setToken`. Both the
host and the credentials land in the same tick the gate opens.

**DD-2 — Early events are DROPPED (no-op), not queued.**

Rationale: `bootstrapPluginInit` calls `switchTicket(bundle.context.ticketKey)`
with the bundle's own ticket key immediately after opening the gate, so a dropped
early event is self-healing in the overwhelmingly common case (the SDK emits for
the same ticket the plugin was mounted for). Queueing would need a second flush
point ordered AFTER bootstrap's own `switchTicket` — otherwise the replay is
instantly overwritten by the bundle key — and that second flush would interact
with `activeKeyRef`'s stale-switch guard for overlapping fetches. That is real
state machinery for a window measured in one SDK handshake.

Residual risk, accepted: if the agent navigates to a DIFFERENT ticket during the
handshake, the panel lands on `bundle.context.ticketKey` rather than the newer
one. This self-corrects on the next `currentTicketUpdated` emission, and is
strictly safer than the status quo (a fetch against the wrong host). The drop
logs via `console.info` so it is visible in DevTools if it ever happens.

**DD-3 — The gate lives in the `currentTicketUpdated` handler, NOT inside
`switchTicket`.**

The review sketch put `if (!ticketKey || !bootstrappedRef.current) return;` inside
`switchTicket`. Do NOT do that: `switchTicket` is also the standalone-dev path
(`grispi-context.tsx:157`) and the context-exported entry point for the dev-only
ticket switcher. Gating it would regress both. The handler boundary is the exact
place WR-01 identifies and the only place the SDK can reach.

**DD-4 — The handler stays REGISTERED synchronously; only its body is gated.**

The review's `.finally()` sketch also moved registration late, which leaves a
window where the SDK may invoke an undefined `plugin.currentTicketUpdated`. The
SDK's behavior there is not ours to own. A registered-but-gated handler is always
safe to invoke.

**DD-5 — Everything else survives untouched.** `activeKeyRef`'s stale-switch
guard, the provisional `{ key }` ticket, and D-14/D-15 no-global-loading on
switch are not modified. Standalone mode sets the same ref for invariant parity
(one line, nothing reads it there — there is no SDK event source in standalone).
</design_decisions>
