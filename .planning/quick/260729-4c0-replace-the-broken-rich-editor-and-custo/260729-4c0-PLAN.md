### Plan 04 — Executable detail/mutation ownership and stable reconciliation

**Files:** `src/query/side-conversation-queries.ts`, `src/query/__tests__/side-conversation-queries.test.tsx`, `src/store/active-conversation-store.ts`, `src/store/__tests__/active-conversation-store.test.ts`, `src/store/compose-store.ts`, `src/store/__tests__/compose-store.test.ts`, `src/screens/chat-screen.tsx`, `src/screens/__tests__/chat-screen.test.tsx`, `src/screens/compose-screen.tsx`, `src/screens/__tests__/compose-screen.test.tsx`.

- `ChatScreen` reads `panelNavigation.selectedConversation` synchronously and calls the tenant/side detail hook; the selection's `sessionKey` gates one-shot focus/scroll and overlay reconciliation so late A results/callbacks cannot affect B. Query owns canonical ticket, comments, solved status, fetch/error, and mutation status. ActiveConversationStore retains only draft HTML, local pending/failed overlays, immutable retry envelopes, lifecycle error presentation, and focus/scroll requests.
- Give payload construction one owner. MobX builds and freezes each exact create/reply/status request once in a `MutationEnvelope` containing `clientMessageId`, kind, tenantId, parentKey, optional sideKey, exact request, sessionKey, and startedAt. UI takes that envelope and invokes the matching Query mutation. Mutation hooks alone call `grispiAPI`; stores never call transport. Hook callbacks call explicit MobX transitions `mutationStarted`, `mutationFailed`, `bindCreatedTicket`, `mutationAccepted`, and `reconcileCanonical`. Retry uses `getRetryEnvelope(clientMessageId)` and passes the same request object back to the same hook; it never rebuilds from current draft or canonical comments.
- Reconcile overlays deterministically. Canonical comments use `comment-${comment.id}`. Each accepted overlay is matched one-to-one, FIFO, against the refreshed own/public canonical comment fingerprint derived from sanitized exact body, creator, ticket, and `createdAt >= startedAt`; record the matched canonical ID and remove only that overlay. Pending/failed overlays keep their stable `clientMessageId`; unmatched accepted overlays remain visible and cannot duplicate another canonical message.
- On every successful create/reply/solve/reopen, await the exact parent-list refresh with `queryClient.invalidateQueries({ queryKey: sideConversationKeys.list(tenantId, parentKey), exact: true, refetchType: 'all' })`, guaranteeing inactive cached lists refresh. Once a side key exists, await exact detail `refetchQueries`/invalidation before `reconcileCanonical` or lifecycle acceptance. Failure paths invalidate/refetch nothing. Create binds the returned side key to the same session before detail refresh; solve/reopen remain non-optimistic, and successful canonical reopen triggers the one-shot composer-focus callback.
- Tests must assert exact request identity on retry, UI hook-to-MobX callback order, failure-without-invalidation, `refetchType:'all'` on inactive parent lists, awaited detail refresh, no optimistic/canonical duplicate, stable failed overlay across refetch, rapid session isolation, create-to-new-side-key binding, quote/internal-note preservation, and solve/reopen focus behavior.
